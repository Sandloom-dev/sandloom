# Changelog — sandloom-redis

## [Unreleased]

## [0.7.0a14] — 2026-11-16

### Breaking changes

- **The Redis drivers take no url and no client bound from a setting, and no instance follows the url of another** (idk-flat-urls-z, idk-flat-urls-no-follows). The `redis` cache, `atomic_store`, `lease` and `broadcast` drivers and the `streams` event bus read their `url` and their bounds from the options of their instance, and an instance with no `url` is refused (`MissingUrlError`). `CACHE_URL` and the `CACHE_*` bounds no longer exist as settings (the kernel refuses them), and the drivers' `settings_fill` is empty. A `broadcast` and the synthesized development `atomic_store` no longer take the url of `cache.default` either: each states its own. The bounds keep the defaults the settings had. The `redis` harness family no longer rewrites a flat variable: it moves the database index of each instance `url`, and of the Celery `broker` through the kernel layout. Upgrade: state the `url` of every Redis instance in `INFRA` ([Upgrading to 0.7.0a14](https://sandloom.dev/docs/operate/upgrade/#upgrading-to-070a14-the-flat-redis-settings)). Two cases need care. An environment whose `INFRA` `cache.default` url differs from the old `CACHE_URL` (a staging setup) must state `atomic_store.security.url` as the old `CACHE_URL` before upgrading, or revocations and blocks written earlier are not seen. A rolling deploy with a declared `broadcast` must state `broadcast.<instance>.url` first, or old and new processes publish on different Redis servers.

### Added

- **A startup warning when a persistent instance shares the cache's Redis database** (idk-flat-urls-no-follows). A `redis` `atomic_store`, a `redis` `lease` or a `streams` event bus whose `host:port/db` is the one of `cache.default` logs one WARNING naming both instances and the endpoint (never a password): a cache that evicts can drop the keys they must keep. It refuses nothing and does not depend on the order the instances start in. An instance the kernel synthesized (not written in `INFRA`: the development `atomic_store` and the default `streams` bus the kernel builds without one) is logged at INFO instead, so the warning keeps its meaning. The drivers register their endpoints in `sandloom.driverkit.shared_endpoints`, drop them when they close, and a path that still holds an `@` (an unencoded password) is never echoed.
- **The `redis` atomic store moves per xdist worker** (idk-flat-urls-z). `RedisAtomicStoreProvider.test_isolation` rewrites the store `url` to the worker's own Redis database through the same driverkit helper the cache uses, so the security store of a worker stays on the worker's cache database (the testing fixtures write revocation and block marks through the cache, the app reads them from the store). A test app whose security store shares its cache url keeps them equal under `-n`.
- **`hiredis` is an optional extra** (idk-low5-product). `pip install 'sandloom-redis[hiredis]'` adds the hiredis parser of the Redis client (`redis[hiredis]>=5.2.1,<6`); the plain install is unchanged.

### Changed

- **An unknown Redis reply is no longer an outage: the five drivers now share one classifier (`sandloom_redis._errors`).** A connection error, a socket `OSError` and the transient replies `LOADING`, `READONLY`, `MASTERDOWN`, `TRYAGAIN`, `CLUSTERDOWN`, `BUSY`, `OOM`, `MISCONF` (the server stops writes after a failed save), `NOREPLICAS` (`min-replicas-to-write` unmet), `MOVED` / `ASK` (a single-node URL pointed at a cluster node) and `UNBLOCKED` (a read cut by a failover) map to `Unavailable` (the reply word is read through the client's `Command # n (...) of pipeline caused error:` annotation too); a timeout to `Timeout`; `AuthenticationError`, `NoPermissionError` and `NOAUTH` / `WRONGPASS` / `NOPERM` to `PermissionDenied`; any other `ResponseError` (an unknown `ERR ...`: an oversized value, a script error) and a client `DataError` to `InvalidArgument`, which is not retryable. Before, the cache, atomic store, lease and broadcast drivers mapped every such reply to `Unavailable`, so the outbox relay (which trusts the mapped class) parked the row for ever as an outage instead of spending an attempt and dead-lettering it. An exception that is not a Redis failure (a `TypeError` of a bug) is no longer mapped at all: it propagates as itself, so it cannot park relay rows as an outage. The lease and the atomic store no longer read a transient reply to `CONFIG GET` as the server refusing the read. The message names the error type only.
- The Streams batch publish chains its `PartialPublish` from the MAPPED error, with the raw Redis error as that error's `__cause__` (it chained the raw error), so the relay judges the batch path like the per-row path: a `PermissionDenied` batch is an outage, an unknown `ERR` reply is not.
- Add the Redis drivers `atomic_store.redis`, `lease.redis` and `broadcast.redis` as an optional package. They left the kernel wheel; `sandloom[redis]` installs this package.
- Add the Streams event bus driver `eventbus.streams` (`sandloom_redis.eventbus.driver`, with its transport in `sandloom_redis.eventbus.streams_*`), moved from the kernel wheel. Its `isolation_identity()` is `streams:<run_id>` of the reached server.
- Add the Redis cache driver `cache.redis` (`sandloom_redis.cache`), moved from the kernel wheel. Its `health()` also runs a no-op script, so a server that refuses scripting reports `fail`.
- **A `redis` instance with no url is refused at startup, and the message names the INFRA option** (idk-flat-urls-s0a). Opening any of the five Redis drivers (`cache`, `atomic_store`, `broadcast`, `lease` and the `streams` event bus; `aopen`, run by the registry at startup) raises `MissingUrlError` (a `ValueError`, `fatal_at_startup`, so startup aborts in every environment, development included) saying `redis atomic_store instance 'security' has no url: set the INFRA option atomic_store.security.url, e.g. INFRA='{...}'`. A `streams` bus with no url of its own still runs on the default cache client and is refused only when that client has no url either. One helper (`sandloom_redis._url.require_url`) does the check for all five. Building a provider and a provider built by hand (`create_redis_cache`, a client or client factory passed in) are unchanged.
- **The Redis test family isolates `INFRA` urls per worker** (idk-flat-urls-s0b). It moves the `url`, `broker` and `backend` of every `INFRA` instance per xdist worker (the Celery task queue's `broker` included), and claims and allocates the indexes of those urls.
- **A `MOVED` / `ASK` reply maps to an `Unavailable` that carries a hint** (idk-low-batch-4). The error has `hint` "cluster redirect: is the client cluster-aware?" (the sentence only, never the address or slot), which the outbox relay prints in its outage warning. The class and `retryable` are unchanged. The hint is set as an attribute after the error is built.

### Fixed

- **The `redis` atomic_store and lease judge `maxmemory-policy` on every new connection, before its first command** (idk-atomic-store-conn-check). A flag cannot judge a socket it did not see: the retrying client and the pool's liveness probe reconnect a dropped socket without raising, and a growing pool opens new ones, after a failover or a DNS repoint possibly to a server that came back evicting. The command that caused the reconnect used to run unchecked on the new socket. Now the pool's connect function sends `CONFIG GET maxmemory-policy` on THAT connection on every connect (the first included); an evicting policy is `InvalidArgument` and a refused read follows `never_evicts_check` (`PermissionDenied` under `verify`), raised before any command is sent. The price is one round trip per new socket. The lease pool, which had no such hook, gets it (an evicted fence key would repeat a fence). A transient failure of the read itself stays `Unavailable` and is no verdict.
- **A client rebuilt for another loop reopens the atomic_store's check**, as the lease's does (idk-atomic-store-conn-check). The check-in-flight race of the old flag (a check that started before a reconnect set the flag after it) no longer matters: each socket is judged by its own connect.
- **A lease health probe on a socket the pool refused answers the policy's reason** (`evicting_policy`, `noeviction_unverifiable` or `eviction_check_refused`), as the atomic_store's does, not the error type of the refusal; the eviction verdict and the policy reader are one shared implementation of both drivers, and a refusal is no `ConnectionError`, so the client's retry never dials and checks again for it (idk-atomic-store-conn-check).
- **The `redis` atomic_store checks `maxmemory-policy` on its first operation, not only in `aopen`** (idk-review-a-fixes). A worker or CLI process never runs `aopen`, so it wrote revocation marks, blocks and idempotency reservations into an evicting Redis without a refusal. The check follows the lease's: `never_evicts_check` `verify` or `assume` behave as in `aopen`, a refusal repeats on every operation and is judged again each time, and a transient failure while reading the policy is `Unavailable` and never counts as a passed check.
- **A `noeviction` lost at runtime refuses the next operation** (idk-review-a-fixes). A `health` probe that finds the policy lost or unreadable (the lease and the atomic_store; also when the probe itself fails with a connection error), and a pooled connection that reconnects (the atomic_store, through the pool's `redis_connect_func`: the retrying client reconnects without raising), open the check again. `health` of the atomic_store no longer repeats a recorded refusal without reading the server: it re-reads every time.
