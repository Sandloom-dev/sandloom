# Sandloom Framework — agent map

This repository is the framework itself. This file and `.claude/` (rules,
skills, agents) are context for working **on** Sandloom; what a new project
gets from `sandloom new` lives in `src/sandloom/core/cli/templates/`.

**Before editing, read the contract for the code you touch** (nearest wins):

| you are changing | read first |
|---|---|
| a business module: `src/sandloom_<module>/`, `examples/*/…/modules/` | `src/sandloom/AGENTS.md` (module-author contract) |
| the kernel: `src/sandloom/core/`, `src/sandloom/sdk/`, `src/sandloom/shared/` | `src/sandloom/core/AGENTS.md` (kernel-contributor contract) |
| deploy profiles, gateway, compose | `deploy/AGENTS.md` |
| the admin console (React) | `admin/AGENTS.md` |

## The one rule

**Modules are atomic and isolated.** Cross-module work goes through typed events,
contracts, projections or sagas, never an import. Every rule is enforced: a failure
prints a code, `uv run sandloom explain <code>` gives why and the fix.

## Golden path (run from the repository root)

```bash
docker compose -f deploy/compose/test.yml up -d --wait  # test Postgres :5433, Redis :6380
uv sync                                                 # pinned dev tools (ruff, mypy, pytest)
uv run sandloom add module <name>                # also: sandloom add event|contract|consumer|saga|projection <module> …
uv run sandloom migrate new <name> "<message>"   # autogenerated revision in the module's chain, RLS included
uv run sandloom generate                         # snapshots, contract stubs + DTO copies, event schemas
uv run sandloom test <name>                      # module tests, fast suite (parallel), static gates
uv run sandloom test --full                      # once, at the end: full parallel suite + gates
```

- **`sandloom generate` writes** the generated files; **`sandloom test` is the gate and
  never writes**. No serial `pytest -q`.
- Parallel runs on one machine each set their own `SANDLOOM_TEST_DATABASE_URL`,
  `SANDLOOM_TEST_CACHE_URL`, `SANDLOOM_TEST_BROKER_URL` and `SANDLOOM_TEST_OWNER`:
  two runs in one checkout share resources otherwise.
- Changing what ships to new projects (`src/sandloom/core/cli/templates/`, the
  `sandloom new` / `sandloom add` output, the public API)? Re-run the DX eval
  (`benchmarks/dx/README.md`). Context for framework work does not need it.

## Where the detail lives

`uv run sandloom docs <name>` (every `sandloom.sdk` name), `uv run sandloom explain <code>`
(every error code), `docs/reference/testing.md` (fixtures, fakes), `docs/adr/` (decisions),
`CONTRIBUTING.md` (issues, labels).

## Looks wrong but is intentional

- `tests/architecture/_fixtures/*.py.txt` — deliberately broken modules the
  analyzer self-tests scan (data, not importable, never shipped).
- `sandloom/shared/contracts/*.py` (stubs, `*_dto.py` DTO copies), `sandloom/shared/events/*.json`
  and each `module.snapshot.json` are written by `sandloom generate`: never hand-edit them.
- `FakeStripeClient` is the default PSP outside prod and rejects unsigned webhooks (sign
  test payloads with `sandloom_billing.psp.sign_stripe_payload`).

## Work is tracked in tm

Tasks, the plan and its state live in tm — not in markdown and not in the
harness's todo list. This checkout's project is the one `.tm/project.yaml`
names; `tm` finds its store through the machine's registry, `~/.tm/tm.yaml`.

- Where work stands and where the last session stopped: `project_status`
  first, not the git log.
- A task is claimed before the first edit (`task_start`) and handed over with
  `task_done`; what may be taken next is `get_active_front`.
- Where the tm MCP server only reads (under OpenCode, agy and pi), the
  tracker is changed in the shell, whose commands carry the session:
  `tm task start <alias|id>`, `tm task done <alias|id>`.
- How any of it is done: the tm skills — `tm-implement`, `tm-plan`,
  `tm-review`, `tm-memory`, and `tm` where none of them fits.

Written by `tm setup` and rewritten whole by its next run; the repository's
own rules and checks belong outside these markers.
