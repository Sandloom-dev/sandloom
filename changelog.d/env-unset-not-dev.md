### Breaking changes

- **An app with `ENVIRONMENT` unset and a database that is not on this machine no longer starts** (env-unset-not-dev). `ENVIRONMENT` still defaults to `dev`, but left unset it now refuses startup with SANDLOOM-B043 when `DATABASE_URL` or the `url` of an `INFRA` database instance names any host other than `localhost`, a loopback address, a unix socket or a file database (`PGHOST`, now a setting of the `ops` tier, counts for a PostgreSQL url that names no host). The app, the worker, the scheduler, `sandloom migrate` and the `sandloom` commands that boot the configuration all refuse. Upgrade: set `ENVIRONMENT=prod` in every deployment (the shipped compose profiles already do), or `ENVIRONMENT=dev` to develop against a database on another host. `sandloom doctor` reports the finding. An app whose database is on this machine starts as before and logs the startup warning.
- **A token from `sandloom dev token` is accepted only where `ENVIRONMENT` is set to `dev` or `test`** (env-unset-not-dev). With `ENVIRONMENT` unset the verifier answers `401` for the token and `mint_dev_token` refuses, where both treated the `dev` default as a development machine. Upgrade: write `ENVIRONMENT=dev` into `.env` (the scaffold already does).

### Security

- **A deploy that forgot `ENVIRONMENT` is no longer silently a development machine** (env-unset-not-dev). A production process with the variable missing accepted a token minted with its key on a developer machine, and lost every production validator. `Settings.environment_explicit` says whether any source of settings (the process environment, `.env`, a secrets file) gave `ENVIRONMENT`; the value of `environment` itself is unchanged, so nothing that reads `settings.environment` or `is_prod` changes. The verification cache is keyed on it.
