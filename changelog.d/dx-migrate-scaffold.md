### Changed

- **`sandloom migrate new` refuses when the models match the chain** (dx-migrate-scaffold). It wrote an empty revision with a random hash. It now stops with "no changes detected" and writes no file; `migrate revision --autogenerate` refuses the same way. `migrate revision` without `--autogenerate` still writes an empty revision, for a data migration.
- **Revisions are numbered in chain order** (dx-migrate-scaffold). `migrate new`, `migrate revision` and `add projection` write `0002_<module>` in `0002_<module>_<message>.py` after the baseline `0001_<module>`, in place of a random hash. A chain of hash ids is counted by its files; `--rev-id` still sets the id. Existing revisions keep their ids. Two branches that each add the next revision of one chain both write `0002_<module>`, which Alembic cannot merge, so `sandloom migrate` (every command) and the migration step of `sandloom test` now refuse a chain in which two files declare one revision id, and name the file to renumber (`renumber 0002_<module>_<message>.py to 0003_<module>`: rename the file, set its `revision` and `down_revision`).
- **A generated baseline enables row-level security in one call** (dx-migrate-scaffold). `enable_tenant_rls(op, "<table>", if_configured=True)` and `disable_tenant_rls(..., if_configured=True)` replace the three-line `if op.get_context().config.attributes.get("sandloom_tenant_rls", False)` guard, which `migrate new` and `add projection` also wrote. A call with `if_configured=True` acts only where the migration runner knows the database enforces tenant isolation (the `tenant_rls` option of its `INFRA` instance). Without the argument both functions behave as before. On a migration context that has no Alembic config (a bare `MigrationContext.configure`) the call with `if_configured=True` raises instead of doing nothing, since it cannot tell whether row security is on; the three-line guard it replaces raised there too. A revision you already have keeps working.
- **`sandloom add module` writes no `settings.py`** (dx-migrate-scaffold). Most modules need none, and the list route takes a default `limit` of 20. `--settings` writes it with `<MODULE>_DEFAULT_PAGE_SIZE`, as before. Upgrade: a module you generated keeps its `settings.py`.
- **`models/__init__.py` of a generated module imports nothing** (dx-migrate-scaffold). The migration runner imports every submodule of the module's `models` package, as `define_module` does (skipping a `tests` or `migrations` package below it), so a model file you add needs no import line. A model outside the package is still not seen.
- **`sandloom add consumer` writes `name=` and a test** (dx-migrate-scaffold). The handler is `@on(Event, name="<function>")`, so renaming the function keeps the consumer group. The test delivers the event twice with `deliver(..., times=2)` and asserts the consumer is registered; add an assertion on your effect. A rename of `name=` is a new group that replays the stream (`docs/modules/between/events.md`, "Do not rename a consumer").

### Added

- **`sandloom add module <m> --entity <name>` and `--empty`** (dx-migrate-scaffold). `--entity order` names the example `ShopOrder`, `shop_orders`, `/orders` and `shop.order.created.v1`. `--empty` writes the package and its migration chain with no table, route or event; the first model you write gets its revision from `sandloom migrate new`. The two exclude each other. An entity whose `<entity>_id` is a column the example already writes (`tenant` and `owner`, since the row has `tenant_id` and `owner_id`) is refused; with `--no-tenant`, `tenant` is allowed.
- **`sandloom migrate new` warns about a `NOT NULL` column with no `server_default`** (dx-migrate-scaffold). A Python `default=` is not a database default, so autogenerate renders `add_column(..., nullable=False)` and the revision fails on a table that has rows. The warning names each column and says to add a `server_default=` or to add it nullable, backfill, then tighten it.
- **`sandloom generate` warns about a consumer view that no longer matches its producer** (dx-migrate-scaffold). It runs the `SANDLOOM-C025` check and prints each finding as a warning that does not fail the command; `sandloom test` still fails on it.
- **`if_configured` on `enable_tenant_rls` and `disable_tenant_rls`** (dx-migrate-scaffold). A keyword-only `bool`, default `False`.
