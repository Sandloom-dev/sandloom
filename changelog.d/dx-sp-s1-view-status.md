### Breaking changes

- **`View(name, row)` is removed; `Projection.view(row)` replaces it** (dx-sp-s1-view-status). `from sandloom.sdk.projections import View` is an `ImportError`. `View` resolved the projection by name at the first request, so a typo was a `LookupError` there and any module could read another module's projection by name, with no owner check. `Projection.view(row, *, on_stale="serve", wait_ms=None)` binds the object: a misspelt projection is a `NameError` when the file is imported, and only a module that can import the projection reads it. Upgrade: `Annotated[ProjectionView[Row], View("notes.board", Row)]` becomes `Annotated[ProjectionView[Row], BOARD.view(Row)]`, with `BOARD` imported from the module's `projections.py`; the keywords are unchanged. A module that read another module's projection by name declares a projection of its own, fed by that module's events. `view` refuses an `on_stale` other than `"serve"` or `"source"` and a negative `wait_ms` with `SANDLOOM-B012` when it is called. `ProjectionView` stays in the advanced tier.

### Added

- **`saga_status(saga, id, with_row=loader)` returns `(handle, row)`** (dx-sp-s1-view-status). It reads the saga instance first and awaits the loader after it in the same unit, so a status route no longer orders the two reads by hand: a saga transition commits the row and the status together, and the row read second is at least as new as the status read first. `handle` is `None` for a saga that never started. It is correct only when the row lives in the saga's database and a local step writes it; the docstring says so, as the call cannot check a loader. `with_row` takes the loader (`lambda: Rows.get_or_404(id)`), and a coroutine passed in its place is a `TypeError` that names the fix. Without `with_row` the call and its result are unchanged. The academy example's status route uses it.

### Changed

- **A lambda is allowed as saga `args`, with a rule** (dx-sp-s1-view-status). The guide called a lambda an anti-pattern and ADR-0008 recommended against it. A lambda now suits a one-expression mapping of `c.input`. A mapping that reads `c.result(...)` or `c.key(...)` is a named function, for two reasons: that is where impurity on a retry creeps in (arguments are recomputed on every attempt, and a drift parks the saga), and the startup check names a function by `fn.__name__` in its errors, which a lambda reports as `<lambda>()`. The docstring of `step`, the saga guide and ADR-0008 say the same; the runtime and the startup check are unchanged.
