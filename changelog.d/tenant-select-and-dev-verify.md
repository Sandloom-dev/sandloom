### Changed

- **The tenant selection errors carry a `code` and say what to do** (tenant-select-and-dev-verify). `TenantScope` answers a request with no tenant `400` with `code` `tenant_required` and a `detail` that names the header the route reads and says its value is an organization id that the access token lists. It answers an organization the token does not list `403` with `code` `tenant_not_authorized` and a `detail` that names the header and says to refresh the access token or log in again when the user joined or created the organization after the token was issued. The `400` for a token that lists several organizations and no header now has `code` `tenant_required`, and the `403` of `TENANCY_MODE=single` for another tenant has `code` `tenant_mismatch`; both keep their `detail`. A `MissingTenantError` at the request boundary answers `400` with `code` `tenant_required`; its text says the route bound no tenant and needs a tenant scope, and offers the client no header. The HTTP statuses are unchanged; the `detail` text is part of the API, so a client that compared it with `tenant context required` or `tenant is not authorized by the access token` compares the `code` now. The kernel text names no module route. See "Upgrading to 0.7.0a16: tenant selection errors carry a code" in `docs/operate/upgrade.md`.
- **`POST /api/v1/orgs` derives `slug` from `name`** (tenant-select-and-dev-verify). `slug` is optional: lowercase, every run of characters outside ASCII `a-z0-9` becomes one `-`, trimmed and cut to 100 characters. A derived slug that is taken answers `409` asking for `slug`. A name that leaves fewer than two characters (`{"name": "A"}`, or a name in another script) answers `422` "the name does not produce a valid slug: pass an explicit slug". An explicit `slug` is validated as before.

### Added

- **`links_are_logged()` in `sandloom.sdk.infra`** (tenant-select-and-dev-verify). It answers whether `NOTIFIER_LOG_LINKS` is on and the notifier instance (default `default`) is the `log` driver, the only one that acts on the setting. A module that prints a token for a dev without a frontend asks it, so the token never reaches stderr next to a delivered mail.
- **Identity prints the API form of the e-mailed steps in dev** (tenant-select-and-dev-verify). With `NOTIFIER_LOG_LINKS=true` and the `log` notifier driver, registration and resend print `[dev only] no frontend? POST /auth/verify-email {"token": "..."}` and a password reset request prints the `POST /auth/reset-password` form on stderr after the change commits, so an app without a frontend can finish the step. Nothing is printed without the setting (refused in production without the accepted risk `log_links_in_prod`), with the `smtp` driver or another driver, or with a custom `email_sender`; no setting verifies an account by itself.
