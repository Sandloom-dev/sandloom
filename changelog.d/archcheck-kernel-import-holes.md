### Breaking changes

- **An application manifest that exempts a package from the import check, lists the kernel in `test_api` or `shared_api`, or excuses it in `allowlist` is refused by every command that reads it (SANDLOOM-C040, C041, C042)** (archcheck-kernel-import-holes). After the `public_api` refusal (C038) three other keys of `architecture_rules.yml` still let a business module reach `sandloom.core`. `kernel_package: m` and `framework_packages: [m]` take the package `m` out of the import check and out of the business modules. `test_api: [sandloom]` was never validated, and a module's tests import everything it lists. `allowlist: [{file: "*", imports: ["sandloom.core*"]}]` excused the whole kernel for every file. `load_rules` now raises, so `sandloom check` exits with 2 before it scans a module, and `generate`, `test`, `add` and `add deploy` stop with the same code. There is no warning phase.
  - **C040** `kernel_package` and `framework_packages` are for the framework's own tree only: top-level modules, `kernel_package: sandloom`, and the running kernel as `sandloom` under `modules_path`. An application sets neither. A manifest that only spells `modules_package: ""` and `kernel_package: sandloom`, or that makes a `sandloom/core` directory by hand, is refused too: the check compares resolved paths with the real kernel.
  - **C041** `test_api` and `shared_api` may not list `sandloom`, `sandloom.core`, or a `sandloom.core` module that is not a test surface. `sandloom.core.testing`, `sandloom.core.contract_testing` and `sandloom.sdk.testing` stay valid. `shared_api` gets the same refusal as `test_api`, which goes beyond the task's wording.
  - **C042** an application's `allowlist` excuses no kernel module: every entry whose `imports` admit `sandloom.core` or a private layer of `sandloom.sdk` is refused (`["sandloom.core"]`, `["sandloom.core.database*"]` and a glob such as `sandloom.cor?` included). The framework's own tree keeps the narrow form: specific imports (`sandloom.core.database*`, not `sandloom.core*`, `sandloom*` or `*`) under a `file` of one module. An entry that admits nothing of the kernel (`file: "*"` with `sqlalchemy*`) is not touched.
  - A malformed `allowlist` (not a list, an entry that is not a mapping, an entry without `file` or `imports`, a value that is not a string) now raises a `ManifestError` naming the entry. It used to be ignored without a word, or fail with an `AttributeError` when the first import reached it.
  - `sandloom add` now reports every manifest refusal (C038, C040, C041, C042) as the refusal. It sent a refused manifest to "run from the project root" for all but C038.
  Upgrade: run `uv run sandloom check`. Delete `kernel_package` and `framework_packages` from the manifest of an application, delete the kernel entries from `test_api` and `shared_api`, and delete each `allowlist` entry that names the kernel. Then move each import the check reports to `sandloom.sdk`. The messages and `uv run sandloom explain SANDLOOM-C040` (C041, C042) say what to delete. The repository's `architecture_rules.yml` and the six examples need no change.
  Docs: [upgrade](docs/operate/upgrade.md), [error codes](docs/reference/error-codes.md).

### Security

- **`framework-imports` (SANDLOOM-C002) reads `sys.modules` as an import** (archcheck-kernel-import-holes). `sys.modules["sandloom.core.database"]` is an import that never says `import`: it hands a module the kernel without any statement the check read. The rule now judges a read of `sys.modules` by the key it can name, with the same branches as `import <key>`, and reports it as `sandloom.core.database via sys.modules`. The key may be a literal, a constant fold (`"sandloom." + "core"`, an f-string over constants), or a name bound once to a constant string.
  The scan follows `sys` under any name: an alias, a chain of aliases in any order, `from sys import modules`, `from sys import *`, `os.sys`, `importlib.sys`, `__import__("sys")`, `importlib.import_module("sys")`, `sys.modules["sys"]`, a walrus. It follows `sys.modules` through an alias, `getattr(sys, "modules")` (and `builtins.getattr`, an alias of it), `vars(sys)["modules"]`, `sys.__dict__`, `attrgetter("modules")(sys)`, and reads by subscript, `get`, `pop`, `setdefault`, `__getitem__`, `in`, assignment and `del`.
  A use it cannot follow is refused under the same rule, as a `sys_modules` violation: a key it cannot read that may name the kernel (a variable, `f"sandloom.{x}"`, `"..." % x`, `.format`, a call), the bare key `"sandloom"` (the package hands out its `core`), the whole mapping (`.items()`, `.keys()`, `.values()`, `.copy()`, `.update()`, a loop, `dict(sys.modules)`, an argument, a stored alias), and `sys` itself handed to other code. Allowed: `sys.modules[__name__]`, a constant key of another package, and a key that starts with a prefix that cannot be the kernel (`"django." + name`), and `sys.argv`, `sys.exit` and the rest of `sys`.
  Upgrade: run `uv run sandloom check`. Import what the module needs from `sandloom.sdk`. A read that is not the kernel but is reported (`sys.modules.items()` in a diagnostic) is waived on its line with `# sandloom: allow framework-imports <reason>`, which is reviewed like raw SQL. Nothing changes at runtime. The kernel's own files, `framework_packages` modules, a module's tests and migrations are not scanned, as for imports. `uv run sandloom explain SANDLOOM-C002` lists what the scan still does not see: `pkgutil.resolve_name`, `importlib.util.find_spec`, `eval` and `exec`, and a module's tests.
  Docs: [upgrade](docs/operate/upgrade.md), [error codes](docs/reference/error-codes.md).
