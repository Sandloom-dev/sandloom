### Breaking changes

- **A `TenantScoped` model is refused when it is defined if its plain insert would reach another tenant through the database** (tenant-orm-insert-gaps).
  The cursor guard sees the values and the filters of a statement, not what the database does with an insert whose every value is the bound tenant's. Three declarations let it reach another tenant's row, and each raises `UnsafeTenantModelError` (an `UnsafeTenantOperationError`) with its own code before any table or row exists.
  `SANDLOOM-R019`: a `REPLACE` conflict clause (SQLite's `sqlite_on_conflict="REPLACE"` on a primary key, a unique constraint or a column) deletes the row that holds the key, whichever tenant owns it. `SANDLOOM-R020`: a foreign key from a tenant table to another tenant table that leaves `tenant_id` out lets the insert lock and probe a parent row of another tenant, which PostgreSQL does outside row-level security; the error names the composite key to use. `SANDLOOM-R021`: a tenant column whose type is not exactly SQLAlchemy's `Uuid` (a `TypeDecorator`, a `UserDefinedType`, a subclass, a `type_coerce`) can store a tenant other than the one the guard bound, which `tenant_upsert` also relied on.
  The check reads every table the mapper of a `TenantScoped` class maps, however it was declared (`__table_args__` or a column keyword, `mapped_column` or `Column`, a mixin, inheritance, imperative mapping, one `Table` under two models), and refuses a constraint or a column attached to such a table afterwards. It runs once when the model is defined; no statement pays for it.
  **Upgrade:** a foreign key to another tenant table becomes composite, `ForeignKeyConstraint(["tenant_id", "parent_id"], ["parent.tenant_id", "parent.id"])`, over a `UniqueConstraint("tenant_id", "id")` on the parent, with a migration for an existing table. A model with `sqlite_on_conflict="REPLACE"` drops it or uses a composite key. A tenant column of another type becomes `Uuid`, and the conversion moves to a column that is not the tenant. A foreign key to a table without `tenant_id`, and one from a table without it, are not affected.
  Docs: [Multi-tenancy](docs/modules/database/multi-tenancy.md#what-the-database-does-with-a-plain-insert), [ADR-0018, decision 7](docs/adr/0018-tenant-guard-at-the-cursor.md) (G-TENANT-28).

### Changed

- **`tenant_upsert` reads the options a model declares and says so** (tenant-orm-insert-gaps).
  The helper refuses a model that declares a `<dialect>_on_conflict*` option of any value on a column, a constraint or an index (`SANDLOOM-R018`), as before. The declared options are read, never the live database schema, so a table built by hand or by a migration with a clause the model leaves out is not read; R018, G-TENANT-27 and the docs now say so. The docstring also states that a driver that batches the parameter sets into one statement (psycopg2) hands PostgreSQL a repeated key twice in one `ON CONFLICT DO UPDATE`, which it refuses.
