### Security

- **The log and Sentry scrubber hides a url's whole userinfo and its secret query values** (scrub-dsn-credentials-gaps). `scrub_text` (`sandloom.core.observability.guardrails`) matched `scheme://user:password@` with a password that holds no `/`, `@` or space, so a password with a raw `@` (`postgresql://u:p@ss@h/db` printed `***@ss@h/db`), an unencoded `/` or a space was printed in part, and the value of a `?password=ab;cd` or `)`-holding query parameter kept its tail; a `?sig=`, `?key=` or `?auth=` value was not masked at all. The userinfo now runs from `scheme://` to the last `@` of the line, without crossing another `scheme://`, and the value of a query parameter whose name ends in `password`, `passwd`, `pass`, `pwd`, `secret`, `token`, `key`, `sig`, `signature`, `auth` or `credential(s)` is masked up to the next `&`, `#`, space or `;` that starts another url: the rules of the masker of `sandloom config`, `sandloom doctor` and the migration logs (`sandloom.core.migrations.url_mask`), which `observability` cannot import (kernel layers), so `test_scrub_text_equivalence` runs both on the same urls. A line that holds a later `@` after a url (a mail address) is masked too far, never too short. `scheme://user@host` without a password now prints `scheme://***@host` too, since the user slot may hold a token. No upgrade step.
- **A very long word in a log line that holds a `://` no longer slows the scrubber down** (scrub-dsn-credentials-gaps). The credential pattern rescanned the rest of a letter-and-digit run from every position, so a 32 000 character token in a message with a url in it took seconds per log record; a scheme is now at most 32 characters and the scan is linear.
