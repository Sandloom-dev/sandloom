### Security

- **The tenant guard's limits at the cursor are named: a `before_cursor_execute` listener with `retval=True`, and a dialect listener that runs the cursor itself, act after the guard read the statement or instead of it** (tenant-guard-cursor-listener).
  The cursor rule reads the compiled statement of the execution context, inside `dialect.do_execute`. SQLAlchemy runs the `before_cursor_execute` listeners before that call, on the engine, on a connection and on the `Engine` class alike, so a listener registered with `retval=True` can send other SQL text or other parameters than the ones the guard checked, and reach another tenant's rows. It runs the dialect listeners (`do_execute`, `do_executemany`, `do_execute_no_params`) before that call too, and skips the dialect method when one returns `True`. A listener that runs the cursor itself and returns `True` therefore skips every check of the cursor hook for that statement: the tenant rule, the data-modifying CTE check, write admission (SANDLOOM-R007), the owner check (SANDLOOM-R013), the money rule (SANDLOOM-B014) and the `tenant_rls` setting sync. Row-level security still filters, by the setting an earlier statement of the transaction set. For the tenant rule the reach is that of `Connection.exec_driver_sql`, which the guard has no compiled statement for. G-TENANT-25 now lists both under "Not covered", ADR-0018 records them as decision 8, and the multi-tenancy page names them under "Cases the check does not see". A `before_execute` listener with `retval=True` is not part of it: it replaces the clause before it compiles, and the guard refuses the replacement.
  No refusal is added, and no code changes. A startup scan of the engine's listeners costs nothing per statement but misses a listener registered later, a connection's and the dialect's, and tells a `retval=True` listener apart by a private SQLAlchemy name. A per-statement comparison of the SQL text costs 12.4 ns a statement in a microbenchmark, does not see replaced parameters or a dialect listener, and would refuse every `insertmanyvalues` batch, whose rewritten statement SQLAlchemy sends itself. The numbers are in ADR-0018 decision 8. Unlike `exec_driver_sql`, no static check flags `event.listen` on these events in module code. A rule for that needs its own error code and is a separate task.
  Docs: [ADR-0018, decision 8](docs/adr/0018-tenant-guard-at-the-cursor.md) (G-TENANT-25), [multi-tenancy](docs/modules/database/multi-tenancy.md).
