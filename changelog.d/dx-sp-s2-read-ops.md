### Breaking changes

- **A read of an operation no module declares is refused** (dx-sp-s2-read-ops). `Reads.one` and `Reads.page` (so `PlannedReads`, `SnapshotReads`, `UowReads`, `read_scope` and a planned `@contract.read`) raise `UndeclaredOperation` (a `PlanningError`, code SANDLOOM-R022, `sandloom explain R022`) at the first read of a `ReadOperation`, `ListOperation` or `JoinRead` that no loaded module declared. The message names the fix: declare the operation at module level in the module that owns its entity, usually in `services/operations.py` imported by the module's `api.py` or services. Before, such an operation (built inside a handler, or in a helper no module imports) compiled lazily and ran with no startup planning and no line in `/diagnostics/core`. The check runs once per operation and adapter, on the plan-cache miss: the cached path of a declared read is unchanged. A handle on a fixed `adapter=` and `session_reads(db())` skip it. Upgrade:
  1. Move an operation built at request time to module level (`item_by_id = ReadOperation(...)` next to the models it reads), and import that file from the module's `api.py` or services. Discovery registers it at boot.
  2. A module that already lists its operations in `setup=` through `core.register_operations(*OPERATIONS)` keeps working: the call is idempotent. Delete it (and the `setup` when nothing else is in it) to get the short form.
  3. An operation over a table no module package holds (a kernel table, an app-level shared model) is never discovered: keep `core.register_operations(op)` in the `setup=` of the module that reads it.
  4. A test that builds an operation in its body and reads it through `Reads(core)` declares it first with `ModuleAPI(core).register_operations(op)`, or reads it with `session_reads(db)`.

### Changed

- **`define_module` registers the planner reads a module declares** (dx-sp-s2-read-ops). Discovery finds every `ReadOperation` (`ListOperation`, `JoinRead`) held in a module variable of the package, directly or one level inside a tuple, list or dict (`OPERATIONS = (a, b)`, a dict a factory filled). An operation counts when its entity belongs to the package: an operation another module defines and this one imports is not registered twice. They register in name order, in one `register_operations` call, before `setup` runs. No new public name: `ReadOperation` was already in `sandloom.sdk.data`.
- **`ModuleAPI.register_operations` is idempotent per operation** (dx-sp-s2-read-ops). A second call with an operation already registered through the same `ModuleAPI` adds neither a second startup task nor a second registry entry; a call that mixes known and new operations registers the new ones.
- **The declared operations are recorded when a module registers, not when its startup task runs** (dx-sp-s2-read-ops). The registry behind `/diagnostics/core` (`planner.operations`) is filled by the module's registration commit (rolled back with it if the commit fails) and keyed by operation, not by name: two modules may name operations alike, and both are planned and listed (the later used to replace the earlier). A test app that never runs its startup tasks, as the harness does, now knows its modules' operations, and `/diagnostics/core` lists them before startup; the plans themselves are still built at startup.
- **The seven modules that registered their operations by hand drop the boilerplate** (dx-sp-s2-read-ops). `sandloom_billing`, `sandloom_identity` and `sandloom_tenancy` and the examples' taskboard, notifications, links and tickets modules no longer import `OPERATIONS` into `__init__.py` or call `register_operations`; notifications, links and tickets are a plain `register = define_module(...)`. The `prepare_declared_operations` startup task of `sandloom_identity` now runs before its `warm_dummy_password_hash` task (discovery registers before `setup`).
- **A when-to-use table of the five read paths** (dx-sp-s2-read-ops): `docs/modules/database/units.md` ("Which read path") and `docs/advanced/execution-planner.md` say operations are discovered, an undeclared one is refused, and `register_operations` is idempotent. `docs/operate/upgrade-1.0.md` has the row and the "Planner reads are discovered" section, and the `define_module` docstring no longer lists planner operations under `setup`.
