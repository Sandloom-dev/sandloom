### Changed

- **Migrations run with a PostgreSQL `lock_timeout`** (migrations-lock-timeout). The connection of each migration chain now sets `lock_timeout` (`MIGRATION_DDL_LOCK_TIMEOUT_MS`, default 5000) and `statement_timeout` (`MIGRATION_STATEMENT_TIMEOUT_MS`, default 0, none) right after the runner takes its advisory lock. An `ALTER TABLE` queued behind a long transaction used to hold its lock request and block every query on the table for as long as it waited; it now fails after the timeout, and the error names the setting to raise. `MIGRATION_LOCK_TIMEOUT_SECONDS` is unchanged: it still bounds the wait for another migrator's advisory lock. **Upgrade:** a revision whose DDL waited more than 5 seconds for a table lock now fails and rolls back; retry it when the long transaction has ended. To keep the old behaviour for a run set `MIGRATION_DDL_LOCK_TIMEOUT_MS=0`, or for one revision write `op.execute("SET LOCAL lock_timeout = 0")` at its start (it lasts to the end of the run's transaction). A `0` value overrides a `lock_timeout` set on the server, database or role. SQLite runs no chain and is unaffected.
