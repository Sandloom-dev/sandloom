### Security

- **A data-modifying CTE could write across tenants** (tenant-guard-cte-dml). Under a bound tenant, `insert(Other).add_cte(update(Item)...cte())` (or any statement with an INSERT/UPDATE/DELETE CTE) rewrote or deleted another tenant's rows, because the tenant criteria only scope SELECTs. The check now reads the compiled SQL at the cursor of every engine the framework builds, so it covers a session, `session.connection().execute` and an engine, and every place the statement tree can hang a CTE (loader options, multi-row `VALUES`, a function statement, a lightweight `table()` or a second `Table` object for the same table). A statement whose DML CTE reaches a `TenantScoped` table, matched by schema and name, is refused with `UnsafeTenantOperationError` (`MissingTenantError` with no tenant bound). A DML CTE holding `text()` or loader options is refused too, because the tables it touches cannot be read. SELECT-only CTEs and DML CTEs on non-tenant tables are unchanged; `unscoped()` still admits trusted system work. An engine built outside the framework's drivers carries no cursor check.
- **`unscoped()` is bounded by its block** (tenant-guard-cte-dml). A task created inside the block copied the context with the bypass set and ran unguarded for its whole life; the bypass now ends with the block, so a task still running after it is guarded again. Await such a task inside the block, or give it its own `unscoped()`. Nested blocks hold the bypass while any is open, and an event consumer's delivery always runs guarded, even when its bus task was first started inside an open `unscoped()`. A non-scope value in the bypass variable no longer crashes every guarded statement.
