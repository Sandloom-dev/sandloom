### Security

- **A data-modifying CTE could write across tenants** (tenant-guard-cte-dml). Under a bound tenant, `insert(Other).add_cte(update(Item)...cte())` (or any statement with an INSERT/UPDATE/DELETE CTE) rewrote or deleted another tenant's rows, because the tenant criteria only scope SELECTs. The check now reads the compiled SQL at the cursor of every engine the framework builds, so it covers a session, `session.connection().execute` and an engine, and every place the statement tree can hang a CTE (loader options, multi-row `VALUES`, a function statement, a lightweight `table()` or a second `Table` object for the same table). Matching the tables a DML CTE reaches kept missing shapes (`quote=False` names, `schema_translate_map`, tables named only through columns, SQL-expression defaults), so no table is matched: **behaviour change**, any statement with an INSERT/UPDATE/DELETE CTE is refused with `UnsafeTenantOperationError` (`MissingTenantError` with no tenant bound) unless inside `unscoped()`, including a DML CTE on a table that is not `TenantScoped`, which was allowed before. Wrap such a statement in `unscoped()`. SELECT-only CTEs are unchanged. An engine built outside the framework's drivers carries no cursor check.
- **`unscoped()` is bounded by its block** (tenant-guard-cte-dml). A task created inside the block copied the context with the bypass set and ran unguarded for its whole life; the bypass now ends with the block, so a task still running after it is guarded again. Await such a task inside the block, or give it its own `unscoped()`. Nested blocks hold the bypass while any is open, and an event consumer's delivery always runs guarded, even when its bus task was first started inside an open `unscoped()`. A non-scope value in the bypass variable no longer crashes every guarded statement.
