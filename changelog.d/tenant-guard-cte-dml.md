### Security

- **A data-modifying CTE could write across tenants** (tenant-guard-cte-dml). Under a bound tenant, `insert(Other).add_cte(update(Item)...cte())` (or any statement with an INSERT/UPDATE/DELETE CTE) rewrote or deleted another tenant's rows, because the tenant criteria only scope SELECTs. The guard now refuses, with `UnsafeTenantOperationError`, any statement whose CTEs hold DML that touches a `TenantScoped` table, as target or in a subquery, wherever the CTE is attached (`add_cte`, `FROM`, `WHERE`, subqueries, nested CTEs). SELECT-only CTEs and DML CTEs on non-tenant tables are unchanged; `unscoped()` still admits trusted system work.
- **A task created inside `unscoped()` kept the bypass after the block** (tenant-guard-cte-dml). The task copied the context with the bypass set and ran unguarded for its whole life. The bypass now ends with the block: a task still running after the block exited is guarded again. Await such a task inside the block, or give it its own `unscoped()`.
