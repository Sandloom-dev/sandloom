### Fixed

- **The test `sandloom add consumer` writes passes right after `sandloom add event`, in either order** (dx-dog-consumer-tenant). `add event contacts ContactCreated --field name:str` gives the event `tenant_id: UUID`, but `add consumer deals contacts.contact.created.v1 --field name:str` wrote a view of `name` alone. Its generated test built `ContactCreated(name="sample")`, and `deliver` refused it with SANDLOOM-R004, `"tenant_id" is a required property`. With the producer found (its class in the tree, or its exported schema), the view now keeps every required field of the producer, (the schema of a producer class requires all its fields, defaulted ones included). A defaulted field is written with the producer's default, because a view field without one is SANDLOOM-C025; a computed default (a call, a factory) cannot be copied, so the generator refuses and you write the view by hand. A `--field` the producer does not send is refused with the producer's fields named, since it would be required in the view and fail every payload of the channel. Without `--field` the view still takes all the producer's fields. With no producer yet, the view is the `--field`s plus `tenant_id: UUID`, the field `add event` writes by default, so a consumer added before its event passes once the event exists. A `tenant_id` you name yourself is not added twice.
  Upgrade: nothing to change in a consumer already written. Re-running `add consumer` appends a second view, so edit an existing view by hand: add the producer's required fields and give the test event a value for each.

### Added

- **`sandloom add consumer --no-tenant` for an app without tenants** (dx-dog-consumer-tenant). It matches `add module` and `add event`: a view built from `--field` alone, with no producer schema found, gets no `tenant_id`. Pass it to `add event` and `add consumer` alike. A view of a found producer takes that producer's fields, so the flag changes nothing there.
