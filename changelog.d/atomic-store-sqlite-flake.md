### Fixed

- **The `database` atomic_store driver on SQLite no longer times out a healthy write that queued behind other writers** (atomic-store-sqlite-flake). The statement deadline (`statement_timeout_seconds`, 5 s) started before a write had SQLite's single write lock, and the waiting writers of a burst polled that lock through the busy handler in no order, so on a loaded host an unlucky one spent the whole deadline waiting and raised `Timeout` (`set_subject_state` in a burst of 54 writers failed in 249 of 600 rounds under load). The writes of one store instance now take turns on a FIFO `asyncio.Lock` (the running event loop's, dropped in a forked child; a waiter keeps one pending acquire, so the queue stays in arrival order) before the deadline starts, so each write gets its whole deadline. A queue that stands still behind a lock the instance does not hold (an external transaction) fails with `Timeout` near the deadline, not one deadline per writer, and the SQLite busy handler now gives up at `statement_timeout_seconds` (`connect_args` `timeout`; it was a fixed 5 s) and maps to `Timeout`, as it was `Unavailable` before. A second store instance on the same file, the module's own engine and another process still contend through that busy handler. Reads and PostgreSQL take no turn. No setting changes.
