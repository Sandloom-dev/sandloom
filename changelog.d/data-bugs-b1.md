### Fixed

- **`conflict_insert` works on a `TenantScoped` model under a bound tenant** (tenant-upsert-admit). The tenant guard refused every `INSERT` of a `TenantScoped` model that was not an ORM instance, so the documented portable upsert only ran inside `unscoped()`. An `INSERT` with `on_conflict_do_nothing()` or `on_conflict_do_update()` is now admitted when a tenant is bound, in one provable form: the rows are in `.values()` (one dict, or a list of dicts for several rows) and the statement runs with no execution parameters. A row without `tenant_id` gets the bound tenant; a `tenant_id` in `.values()` must be the bound tenant's id as a plain value, and another tenant's id, a `bindparam`, a `literal()` or any expression raises `UnsafeTenantOperationError`. The `tenant_id` slot is a bind named `sandloom_bound_tenant__` and the `DO UPDATE` scope one named `sandloom_upsert_tenant__`; a statement holding another bind of either name (in a column value, `set_`, `where=`, `index_where=`, `returning()` or `text()`) is refused. `DO UPDATE` gains `tenant_id = <bound tenant>` in its `WHERE`, so a conflict with another tenant's row updates nothing. With no tenant bound it is still refused; `set_` naming `tenant_id`, a `set_` key that is not a column of the model (`literal_column("TENANT_ID")`, an unknown name; PostgreSQL would render it verbatim), `from_select`, a subquery (also inside a multi-row `.values()`) and a plain `INSERT` (no `ON CONFLICT`) on a `TenantScoped` model stay refused. `set_` may read the proposed row through `stmt.excluded` (the whole `excluded` row stays refused, as it carries `tenant_id`). Pass the model class, not its `Table` (a Core statement on a tenant table stays refused). Code that wrapped such an upsert in `unscoped()` keeps working; it can drop the wrapper. Code that passes the rows as execution parameters (`session.execute(stmt, rows)`) on a tenant model must move them into `.values()`; that form was never admitted before this release.
- **`open_uow()` without a name opens the calling module's primary database** (open-uow-module-db). It always opened `default`, while `units.md` promised the module's primary database, so a task or service of a module whose migration chain lives on another database wrote to `default`. The module is the one whose package holds the calling code (`ModuleDescriptor.database_instances()`, the resolution a contract's unit uses); code that no loaded module holds, such as a script, still gets `default`, and so does a module whose `define_module(name=)` differs from its package. A module with several required databases, `default` not among them and no `migrations_database`, has no primary one: `open_uow()` now raises `MigrationTargetError` there, on entering the block (as its contracts already do), so it declares `migrations_database` or passes the name; a module that requires `default` and another database gets `default`. The database is resolved when the block is entered, against the core active then, not when `open_uow()` is called. Upgrade: a module on a non-default database that called `open_uow()` and relied on `default` passes `open_uow("default")`; a module on `default`, the standard modules included, is unchanged.
