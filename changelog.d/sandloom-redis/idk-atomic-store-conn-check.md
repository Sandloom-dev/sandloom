### Fixed

- **The `redis` atomic_store and lease judge `maxmemory-policy` on every new connection, before its first command** (idk-atomic-store-conn-check). A flag cannot judge a socket it did not see: the retrying client and the pool's liveness probe reconnect a dropped socket without raising, and a growing pool opens new ones, after a failover or a DNS repoint possibly to a server that came back evicting. The command that caused the reconnect used to run unchecked on the new socket. Now the pool's connect function sends `CONFIG GET maxmemory-policy` on THAT connection on every connect (the first included); an evicting policy is `InvalidArgument` and a refused read follows `never_evicts_check` (`PermissionDenied` under `verify`), raised before any command is sent. The price is one round trip per new socket. The lease pool, which had no such hook, gets it (an evicted fence key would repeat a fence). A transient failure of the read itself stays `Unavailable` and is no verdict.
- **A client rebuilt for another loop reopens the atomic_store's check**, as the lease's does (idk-atomic-store-conn-check). The check-in-flight race of the old flag (a check that started before a reconnect set the flag after it) no longer matters: each socket is judged by its own connect.
