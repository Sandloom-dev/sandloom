## Promise

## Pains and reliefs

All six from the positioning, in this order; shared reliefs share a clause.

| # | Pain (way of working) | Evidence | Relief | Advantage |
| --- | --- | --- | --- | --- |
| 1 | The architecture decays: the first weeks are fast, then each change costs more | He et al., MSR 2026: complexity +41%, stays up, drives the slowdown | Each part stays closed off and a check fails when a boundary breaks, so changes stay quick | Isolated logic; checked architecture |
| 2 | An agent can't design an architecture and hold it in mind | Dente et al., 2026 | The shape is decided: generators and skills give it, the agent only has to understand the part it changes | Skills and toolset |
| 3 | Coupled code does not split across several agents | Anthropic C compiler; Cognition | Separate parts let several agents work at once | Isolated logic |
| 4 | In a complex project the agent is overloaded and misses connected things | Anthropic context engineering | It reads a page of context, and transactions, logins and customer data separation are handled for it | Toolset; reliability and security by default |
| 5 | Rules written in a prompt are only requests | Gloaguen et al.; Replit incident | Rules are checks that fail and name the fix | Checked architecture |
| 6 | Moving to services means rewriting | Fowler, Newman | One application splits into services by configuration, with the same code | Monolith or services; infrastructure independence |

Pain paragraph's linked study and number: He et al., "complexity rose 41% and stayed up". Pains are of the way of working, never Sandloom's own; they follow the promise.
