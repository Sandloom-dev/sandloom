## One message

## Promise

Positioning value: speed of development, reliability, scalability, a split from monolith to services without rewriting. Anatomy wants three mechanisms and three outcomes:

- Who writes: you or your coding agent.
- Mechanisms (owner's main agent advantages, plain words): parts of the product closed off from each other; rules a machine checks; skills and tools that give the agent a starting point.
- Outcomes (*operator*): your backend **stays quick to change as it grows**, **runs reliably**, and **splits from one application into services without a rewrite**.

## Core idea

"Sandloom keeps your business logic atomic and isolated from each other and from the infrastructure." Used in page form, not word for word: "Sandloom keeps each part of your product closed off from the others and from the servers it runs on." The first half (parts closed off from each other) explains the reliefs for decay and coupled code; the second half (from the infrastructure) explains the promise's split into services and database/mail swaps.

## Argument

*Operator:* owner's rule is to pick a reasonable number of the strongest pains and advantages that combine logically, grouped by a shared cause; the choice was left to the writer. The three groups below are taken. Ranked for a `new` reader by felt sharpness and evidence: decay (measured study) > rules are requests (enforced mechanism, incident) > can't hold the architecture (study) > overload (vendor guidance + our size measurement) > subagents (anecdote + one branch test) > rewrite to services (literature, not agent-specific).

Grouped by one criterion, **what the agent depends on**:

1. **The agent has to remember the architecture.** Pains: can't design and hold the architecture; overload in a complex project; rules in a prompt are only requests. Pain sentence: "An agent has to design the structure, keep it in mind and follow rules written as requests, so in a big project it misses what is connected." Relief: generators give it a starting point, project rules tell it how to work, and checks that fail stop it when it breaks a rule (owner's own combination). Advantages: skills and toolset; machine-checked architecture. Evidence: Dente et al. 2026; SaaStr/Replit incident; C001/C006 exit 1.
2. **The code depends on itself.** Pains: the architecture decays, every feature costs more; tangled code does not split across several agents. Pain sentence: "Each change reaches into other parts of the code, so every feature costs more than the last and two agents can't work at once." Relief: each part of the product is closed off from the others and talks to them only through declared calls and messages. Advantage: atomic, isolated business logic. Evidence: He et al., MSR 2026 (lead study, linked: complexity +41%, velocity gains last two months).
3. **The code depends on where it runs.** Pain: moving to microservices means rewriting. Pain sentence: "Calls between parts are tied to one process and one database, so splitting into services means a rewrite while the product is busiest." Relief: start as one application and split by configuration, with the same code; change the database, cache or mail service in configuration. Advantages: monolith or services; independence from the infrastructure. Evidence: mechanism only (`SANDLOOM_MODULES`, `SERVICE_BINDINGS`); data move is a separate step and the relief must not imply otherwise.

Carried without strain elsewhere: reliability and security by default → the promise's "runs reliably"; ready-made modules → a card (sign-in, teams and payments). Left out of the argument: reliability/security as their own group (→ `modules/guarantees/index.md`), "looks done and is not", "every session starts from zero", reinvented plumbing, review speed (agentic-pains rows 6–12; background, → `architecture.md`).

## Evidence

May claim:
- He et al., MSR 2026 (https://arxiv.org/abs/2511.04427): after adopting Cursor, velocity rises only for the first two months; static-analysis warnings +30%, code complexity +41%, and they stay up. One linked study with one number in the pain paragraph.
- Mechanisms, without numbers: a broken boundary or a `commit()` fails a check with a code and the fix (C001, C006, captured exit 1 per agentic-pains); routes require login unless declared public (B008); configuration chooses what runs where.
- "Split without rewriting code", provided the page does not say data moves by configuration.

May not:
- Any time ("20 minutes"), speed-up or "fewer bugs" figure for Sandloom; nothing measured it.
- METR figures; Veracode / GitClear numbers (vendor, background only).
- "Several agents work in parallel" as tested: only two branches were merged, no agents.
- File sizes (2.9 KB `AGENTS.md`), 29 SDK names: true but terms of a deeper level.
