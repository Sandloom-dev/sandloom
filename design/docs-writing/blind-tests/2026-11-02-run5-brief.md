## Purpose (owner's; proposed, question 1)

- **Effect.** A developer or vibe coder wants to try Sandloom and pastes the prompt into their coding agent, or starts the quickstart. An agent that lands here understands what Sandloom is and can follow the prompt literally.
- **Place.** Readers arrive from the site home ("Start building", "Documentation"), the README's Documentation link, the 404 page ("what Sandloom is"), search and `llms.txt`. Next: the agent prompt or the quickstart (to try it), the tutorial (to learn by building), `docs/architecture.md` (to evaluate how it works).
- **Sign it worked.** A reader who never saw Sandloom can say: "a Python backend framework designed for AI-driven development; it keeps each part of the product closed off and checks the rules, so the code stays changeable as the agent adds features", and then tries it.
- **Not its job.** How it works (`docs/architecture.md`), installing and ports (`docs/getting-started/index.md`), guarantees and their conditions (`docs/modules/guarantees/index.md`), the ready-made modules (`docs/modules/standard/index.md`), deployment (`docs/operate/split-into-services.md`).

## Promise (proposed, question 4)

Block 1, three sentences per the entry anatomy:

1. **Sandloom is a Python backend framework designed for AI-driven development.**
2. Who writes the code and the three mechanisms, from the owner's combination of the first three advantages: you or your coding agent write it; generators give the agent a starting point, project rules tell it how to work, and checks that fail stop it when it breaks a rule.
3. What the backend gets, three outcomes from the owner's value (speed, reliability, scalability with no rewrite): it stays quick to change as it grows, runs reliably, and splits from one application into services without rewriting code.

The owner's value names four things; "scalability" and "a split into microservices without rewriting code" are merged into the third outcome. Show the owner (question 4).

## Core idea (question 3)

Owner's phrase, meaning not page text: "Sandloom keeps your business logic atomic and isolated from each other and from the infrastructure."

- **First half** ("atomic and isolated from each other") explains the reliefs: decay, splitting work across subagents, overload, rules being only requests.
- **Second half** ("and from the infrastructure") explains the promise's third outcome: services without a rewrite, and a database, cache or mail service changed in configuration.
- Proposed page form, since "atomic" and "isolated business logic" stop the entry reader: "Sandloom keeps each part of your product closed off from the others and from the infrastructure." It opens the relief paragraph.

## Pains and reliefs (question 2)

The positioning closes the list at six; the entry page carries about five. Proposal: all six, pains that share a relief sharing its clause, the rewrite last since it is not specific to agents.

Pain paragraph opens on the way of working and its cost: agents write features fast, and the first weeks are fast; then, per [He et al., MSR 2026](https://arxiv.org/abs/2511.04427), velocity gains last only the first two months while code complexity rises 41% and stays up.

| # | Pain | Relief, same terms | Advantage | Evidence |
| --- | --- | --- | --- | --- |
| 1 | The architecture decays, and every change and feature costs more | Each part is closed off and the boundaries are checked on every change, so the next feature costs what the first did in kind (no number) | Isolated logic; machine-checked architecture | He et al.; C001, snapshot checks T004/T005/T007 |
| 2 | An agent can't design an architecture and hold it in mind | The shape is decided: generators start every feature from the same layout, and the project rules and skills tell the agent how to work | Skills and toolset | Dente et al. 2026; `sandloom add`, generated `AGENTS.md` and skills |
| 3 | Tightly coupled code does not split across subagents | Each part owns its files, tables and tests, so separate parts can be worked on separately | Isolated logic | Two branches adding modules merged cleanly (2026-11-02); **not tried with parallel agents** |
| 4 | In a complex project the agent is overloaded and misses connected things | The agent only has to understand the part it is changing, and transactions, login checks and each customer's data are not its to remember | Skills and toolset; reliability and security by default | Generated `AGENTS.md` 2.9 KB, `sandloom context` 1.1 KB; B008, C006, C014 |
| 5 | Rules in a prompt are only requests | A broken rule fails a check that names the fix | Machine-checked architecture | C001, C006 exit 1; `sandloom explain` |
| 6 | Moving from a monolith to microservices means rewriting | The same code runs as one application or as services, chosen in configuration | Monolith or services; independence from infrastructure | `SANDLOOM_MODULES`, `SERVICE_BINDINGS`, `sandloom add deploy` |

Pains 1 and 5 share "checks"; 3 and 1 share "closed off".

## Evidence

**May claim:**

- He et al., MSR 2026: velocity rises only for the first two months; static-analysis warnings +30%, complexity +41%, staying up. The one linked study on the page.
- A broken rule fails a check with a code and its fix (C001, C006, exit 1; `docs/reference/error-codes.md`); recapture before showing.
- One command, `sandloom test`, ends with `sandloom test: OK` (quickstart smoke test, `tools/smoke/quickstart_check.py`).
- Every route requires login unless it declares itself public (SANDLOOM-B008); each customer's rows are filtered with policies the migrations write (C014, C015, T006).
- The same code runs as one application or as services by configuration; moving existing data is a separate step (stays one link deeper, not on the first screen).
- Outcomes without numbers ("stays quick to change as it grows", "runs reliably") because the page names the mechanism behind each.

**May not claim:**

- Any speed-up, time saved or failure rate for Sandloom: nothing measured (the DX product suite has not been run; `agentic-pains.md`, Open).
- "About twenty minutes" for the tutorial: published on `tutorial.md`, not measured.
- That several agents work in parallel without conflict: tried with two branches, not with agents.
- METR figures, and any claim that agents go faster at all.
- "Cannot" or "never" about decay inside one part: checks limit dependencies between parts and function complexity, not a tangled part.
- A security claim beyond login checks and per-customer data separation.
