# Sandloom

**Sandloom is a Python backend framework designed for AI-driven development.** Your coding
agent builds the product, or you do. Sandloom gives the code a fixed shape and checks
every change against it. Your backend stays fast to change as the product grows, and a
crash or a retry never leaves a change half-saved. When one application is no longer
enough, your backend splits into separate services without a rewrite.

## Why a backend gets harder to change

Picture a shop an agent built: orders, discounts, invoices, payments. The first features arrive fast,
then each costs more. A [study of GitHub projects that adopted an AI editor](https://arxiv.org/abs/2511.04427)
found the speed gain gone after about two months. Code complexity rose 41%
and stayed up.

First, every piece of code can reach into every other. A change to discounts breaks
invoicing, in a file the agent never opened. The shop outgrows what the agent can keep in
view, and two pieces of work on it at once overwrite each other. Second, the shop's rules exist
only as instructions. The agent decides the layout of each feature on its own, and a rule
in a prompt is a request it can miss. A third cost arrives when the shop needs separate
services: orders call payments and the database directly, and each such call must be
rewritten.

Sandloom keeps each area of the shop in its own part. A part is
[closed off](modules/index.md#what-a-module-may-import) from the other parts, and it
reaches the database and other outside systems only through the framework.
A change to discounts stays inside that part, and the agent needs to read only that part.
Two pieces of work on two parts do not collide.

Each feature starts from the same generated shape, and project rules tell the agent how to
work. A broken rule fails a check, and the check names the fix. Orders never call payments
or the database by name, so moving payments into its own service is a
[change of configuration](operate/topologies.md), with the same code. Through crashes and
retries, the framework saves each change whole: a crash in the middle of an order leaves no
half-saved order.

!!! tip "Start here"

    === "With your coding agent"

        Install Python 3.11 or later, [uv](https://docs.astral.sh/uv/) and Docker, then
        give your agent this prompt:

        ```text
        Create a backend with Sandloom. Follow the quickstart at
        https://sandloom.dev/docs/getting-started/ step by step. Then read the AGENTS.md
        file it generates in the new project and follow it for every change.
        You are done only when `uv run sandloom test` prints `sandloom test: OK`.
        ```

        When the last line reads `sandloom test: OK`, your application has its
        first part and every check passes.

    === "Yourself"

        Install Python 3.11 or later, [uv](https://docs.astral.sh/uv/) and Docker, then
        follow the [quickstart](getting-started/index.md). You finish with an application
        that answers on your machine and a first part that passes every check. The [tutorial](getting-started/tutorial.md) then
        connects two parts into a first feature with its tests.

Agents reading these docs can start from <a href="llms.txt"><code>llms.txt</code></a>, an index of every page.

## Who it fits

Sandloom suits a backend like that shop: several areas of business that people and coding
agents change again and again. For a tiny endpoint or a short
script the structure costs more than it saves. Sandloom also fits poorly with an application
that cannot be divided into parts and with a team that skips the rules and the checks.
