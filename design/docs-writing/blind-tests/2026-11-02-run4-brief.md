## One message

From the positioning (operator, from the owner's record), verbatim: "Sandloom is a Python backend framework designed for AI-driven development."

## Promise

From the positioning's value (owner: speed of development, reliability, scalability, a split into microservices without rewriting), as three outcomes (operator, from the owner's record, round 2: security stays out of the promise and goes to the fit; scalability and the split are one outcome):

1. **Stays quick to change as it grows** (speed). Mechanism: isolated parts, checked boundaries.
2. **Runs reliably** (reliability). Mechanism: the framework owns transactions and message delivery, so a crash or a retry does not half-save a change, lose a message or charge twice.
3. **Grows from one application into separate services without rewriting code** (scalability and the split, one outcome). Mechanism: parts talk only through declared calls and messages, and the database and services are chosen in configuration.

## Core idea

Owner, verbatim: "Sandloom keeps your business logic atomic and isolated from each other and from the infrastructure."

- **First half, "atomic and isolated from each other"**, explains the reliefs: the architecture stays intact (decay), the agent works on one part at a time (design, overload), parts can be changed in parallel, and because parts only talk through declared calls and messages, they can move into separate services (promise 3).
- **Second half, "from the infrastructure"**, explains the backend promise: the database, cache or mail service is chosen in configuration and changes without touching business code; with the first half it makes promise 3 a configuration change.
- The checks (strict, machine-checked architecture) are what make the idea hold rather than a convention; the page states that in one sentence after the core idea.

## Evidence

**May claim:**

- He et al.: complexity up 41% and staying up after adopting an agent tool, with the link. One study, one number, in the pain paragraph.
- A broken boundary fails `sandloom check` with a code and exit 1 (README's representative output; the C001 fix text is stale, task `check-messages-stale`, so do not show its text on the page).
- `sandloom test` is one command; "done" means it prints `sandloom test: OK` (quickstart).
- Every route requires sign-in unless declared public (B008); each customer's rows filtered by the database (C014, C015, T006).
- The same code as one application or services by configuration; existing data moves in a separate offline step.
- Outcomes without numbers, each with its mechanism named: "stays quick to change as it grows", "runs reliably", "splits without rewriting code".
- Sign-in, organizations and billing ship as ready-made parts.

**May not claim:**

- Any speed-up, time saved or token saving. The 167k–257k-token baseline predates current changes; not re-measured.
- "About twenty minutes" for the tutorial and any "in minutes" for the quickstart: nobody measured them.
- That several agents have worked in parallel on Sandloom (only branches, without agents, were tried).
- METR figures; Veracode's 45% and GitClear's figures (vendors; and one study per page).
- "Secure" or "never fails" in general; Sandloom covers routes, sessions and data separation, not general vulnerabilities, and does not catch wrong business logic.
- "Moves to microservices without any migration": data is a separate step. Already-published wording that drops this caveat is not reused.
- That Sandloom stops decay inside one part.
