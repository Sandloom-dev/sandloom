# Verified precedents (second pass: sources opened, code checked where possible)

Treat as input, re-verify anything decisive.

1. ABP Framework — per-module Domain.Shared / Application.Contracts / HttpApi.Client (verified in modules/identity/src). Framework csproj (MultiTenancy, Features, Authorization, Security) reference no modules. BUT ICurrentTenant, ITenantStore, tenant events (framework/src/Volo.Abp.MultiTenancy.Abstractions) and ICurrentUser (TenantId, Roles, FindClaim; Volo.Abp.Security) are framework concepts. Pattern: framework holds interface + Null default (IPermissionStore/NullPermissionStore, IFeatureStore/NullFeatureStore, DefaultTenantStore from config); module implements. Permission↔identity binding lives in the identity module. Users.Abstractions lives in modules/users. FeatureDefinitionProvider usually in Application.Contracts; framework EditionFeatureValueProvider only reads an `editionid` claim; Editions in commercial SaaS module. IAbpClaimsPrincipalContributor lets modules add claims. https://abp.io/docs/latest/framework/architecture/best-practices/module-architecture , https://abp.io/docs/latest/framework/architecture/multi-tenancy , https://abp.io/docs/latest/framework/infrastructure/current-user , https://abp.io/docs/latest/framework/infrastructure/features

Never at module load. https://docs.djangoproject.com/en/5.2/topics/auth/customizing/

10. Enforcement — import-linter forbidden: source_modules, forbidden_modules, ignore_imports, unmatched_ignore_imports_alerting (error default), allow_indirect_imports, include_external_packages. ArchUnit FreezingArchRule. https://import-linter.readthedocs.io/en/stable/contract_types/forbidden/

11. Counter-evidence summary — ABP has tenant/user/roles/edition id in framework; Django defaults to auth.User; Odoo ORM knows res.users; Home Assistant helpers import core integrations; Laravel ships auth contracts and a base User class but the concrete User is in the app skeleton and billing is laravel/cashier-stripe; Rails generates authentication into the app. Pattern: a kernel may ship a generic cross-cutting concept (principal, tenant scope, roles, claims) as an interface with a null/configurable default, never importing module code. No precedent puts billing-domain concepts (subscription, credits, plans) in the kernel. Hard couplings accepted only where core and "module" always release together and the module is mandatory.

First pass's recommendation (to be challenged, not adopted): per-provider contract packages (sandloom-<m>-contracts) depending only on sandloom.sdk; kernel keeps authz mechanism, atoms move to owners' contract packages with resolvers registered by providers; generic principal + claims contributors; membership helper to tenancy contracts or a kernel Protocol; import-linter forbidden contract with shrinking ignore_imports; deprecation shims one cycle; boot test of kernel with no first-party modules.
