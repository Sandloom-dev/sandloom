# Deploy profiles — agent contract

`SANDLOOM_MODULES` (a JSON list) decides what each process loads. The same image
runs both profiles. Full reference: `deploy/README.md`.

| profile | file | topology |
|---|---|---|
| monolith | `compose/monolith.yml` | `migrate` → `app` (every module) + `worker` + `beat`; one Postgres, Redis; HS256 `JWT_SECRET` |
| microservices | `compose/microservices.yml` | nginx `gateway/nginx.conf` → one service per module group, each with its own database and `migrate-<service>` one-shot; Streams bus; wired by `SERVICE_BINDINGS` |

The microservices profile and its gateway are **generated**: `uv run sandloom add
deploy <module>... --service <svc>` (from the repository root) writes everything
between the `# >>> generated by sandloom add deploy` markers, from what the
modules provide and consume. Never hand-edit a generated block (the next run
refuses with a diff); edit outside the markers. The same command splits an
`sandloom new` app (it creates the app's profile from the package's templates).
Guide: `docs/guides/split-into-services.md`.

## Invariants (pinned by `src/sandloom/core/tests/test_deploy_profiles.py`)

`sandloom.core.testing.deploy_profile.profile_problems` checks them (SANDLOOM-T014) on
this profile and, in `sandloom test`'s `schema & deploy` step, on an app's.

- **Shared settings.** Security- and auth-relevant settings live in the
  shared env anchor and are identical in every process: `JWT_*`, token
  lifetimes, `INTERNAL_API_TOKEN`, notifier/SMTP, `BILLING_DENY_ON_PAST_DUE`.
  - The exceptions are the issuer-only `JWT_PRIVATE_KEY` and `JWT_SECRET` on
    the identity processes of the microservices profile.
  - **`CACHE_URL` is shared by all services**: revocation marks, rate limits,
    idempotency keys and the bus live there.
- **Microservices keys.** Tokens use EdDSA: `JWT_PRIVATE_KEY` on identity
  only, and `JWT_PUBLIC_KEYS` + `JWT_KID` everywhere. The profile also
  requires `INTERNAL_API_TOKEN` and per-service RPC keys:
  - each service: `RPC_DH_PRIVATE_KEY`;
  - each calling service: `RPC_PRIVATE_KEY`, which signs its commands;
  - shared: `RPC_SERVICE_DH_KEYS`, `RPC_SERVICE_KEYS` and `RPC_ALLOWED_CALLS`,
    which must equal the services' `SERVICE_BINDINGS`.
- **Bindings.** Each service's `SERVICE_BINDINGS` is exactly the contracts its
  modules consume and do not provide locally, plus `<module>.claims.v1` on the
  issuer for every claims contributor (`"critical": false` iff the
  contributor is non-critical).
- **Probes.** Peers never feed `/health` (liveness). Only `"required": true`
  bindings feed `/ready`.
- **The gateway** re-resolves services through Docker DNS and never routes
  `/_sandloom`, `/diagnostics` or `/metrics`.
- **Every module route prefix is routed** to its owning service by the
  gateway. A new module needs a `location` block, or it is unreachable when
  split: `uv run sandloom add deploy <module> --service <svc>` writes it
  together with the profile entry and the bindings.
- **Workers** are sized from the CPU quota (`WORKER_CONCURRENCY`) and
  health-checked with `python -m sandloom.core.worker healthcheck`. Run exactly one
  beat per broker (it holds a fenced lease).
- **Migrations.** One-shot `migrate` services (`sandloom migrate upgrade-all
  --apply`) run to completion before `app` and `worker` start
  (`depends_on: service_completed_successfully`).

## Adding a module to the microservices profile

`uv run sandloom add deploy <module> --service <svc>` (a new service, or a module
added to an existing one) writes, together:

- an env anchor with the service's `SANDLOOM_MODULES`, `DATABASE_URL` and
  `BROKER_URL`;
- a `migrate-<service>` one-shot;
- the bindings and `RPC_ALLOWED_CALLS`;
- the gateway prefixes;
- a worker (`tasks.py`) and one beat (periodic tasks).

`uv run sandloom add deploy --refresh` re-derives them after a code change; `uv
run sandloom add deploy --check` checks the profile and boots every service alone.

Existing data does not move by itself: skill `sandloom-extract-module`, or the
runbook in `deploy/README.md`. To move a module to its own service end to
end, use skill `sandloom-split-deploy`.

## Checks

- `uv run sandloom add deploy --check` checks the profile
  invariants and boots every service alone;
  `uv run pytest src/sandloom/core/tests/test_deploy_profiles.py -q` pins them.
- `src/sandloom/core/tests/test_module_boots_alone.py` checks that each module
  boots alone.
- The split conformance matrix (`tests/split_conformance`, slow) checks
  that a split deployment answers identically to the monolith.
- CI runs `deploy/smoke/microservices-smoke.sh` against the real compose
  stack, and `tools/smoke/split_check.py` (job `app-split`) splits a fresh
  `sandloom new` app.
