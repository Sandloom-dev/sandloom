# Sandloom Deployment Profiles

Sandloom is a **configurable monolith**: the same codebase and the same Docker
image deploy either as a single process or as a set of services. The split is
pure configuration — the `SANDLOOM_MODULES` environment variable tells each
process which modules to load.

## Profiles

| Profile | File | Topology |
| --- | --- | --- |
| Monolith | `compose/monolith.yml` | `migrate` → `app` (all modules, `:2222`) + `worker` + `beat`, one Postgres DB, Redis |
| Microservices | `compose/microservices.yml` | nginx `gateway` (`:8080`) → `identity` / `tenancy` / `billing`, each with its **own database** and its own `migrate-<service>` one-shot; `identity-worker` + `identity-beat`, `billing-worker` + `billing-beat`; Redis (Streams bus) |

```bash
# Monolith
JWT_SECRET=$(openssl rand -hex 32) TWOFA_ENCRYPTION_KEY=$(openssl rand -hex 32) \
BILLING_PROVIDER=stripe \
STRIPE_SECRET_KEY=sk_live_... STRIPE_WEBHOOK_SECRET=whsec_... \
  docker compose -f deploy/compose/monolith.yml up --build

# Microservices (INTERNAL_API_TOKEN and asymmetric JWT keys are mandatory here)
sandloom keys generate --kid jwt-1 --out-dir ./secrets   # or print and export them
sandloom keys generate --purpose rpc --service identity     # callers: Ed25519 (signs
sandloom keys generate --purpose rpc --service billing      # commands) + X25519 (MAC)
sandloom keys generate --purpose rpc-dh --service tenancy   # provider: X25519 only
JWT_PRIVATE_KEY="$(cat secrets/jwt_private_key)" JWT_KID=jwt-1 \
JWT_PUBLIC_KEYS="$(cat secrets/jwt_public_keys)" \
IDENTITY_RPC_PRIVATE_KEY="..." IDENTITY_RPC_KEY_ID=identity-1 \
BILLING_RPC_PRIVATE_KEY="..." BILLING_RPC_KEY_ID=billing-1 \
RPC_SERVICE_KEYS='{"identity": {"identity-1": "<PEM>"}, "billing": {"billing-1": "<PEM>"}}' \
IDENTITY_RPC_DH_PRIVATE_KEY="..." IDENTITY_RPC_DH_KEY_ID=identity-1 \
TENANCY_RPC_DH_PRIVATE_KEY="..." TENANCY_RPC_DH_KEY_ID=tenancy-1 \
BILLING_RPC_DH_PRIVATE_KEY="..." BILLING_RPC_DH_KEY_ID=billing-1 \
RPC_SERVICE_DH_KEYS='{"identity": {"identity-1": "<X25519 PEM>"}, "tenancy": {...}, "billing": {...}}' \
JWT_SECRET=$(openssl rand -hex 32) INTERNAL_API_TOKEN=$(openssl rand -hex 32) \
TWOFA_ENCRYPTION_KEY=$(openssl rand -hex 32) BILLING_PROVIDER=stripe STRIPE_SECRET_KEY=sk_live_... STRIPE_WEBHOOK_SECRET=whsec_... \
  docker compose -f deploy/compose/microservices.yml up --build

# Microservices, development / CI only: fresh keys in a plain file
(uv run sandloom keys dev-env --out ../deploy/.env.microservices)
docker compose --env-file deploy/.env.microservices \
  -f deploy/compose/microservices.yml up --build

# Demo stack without Stripe (either profile)
BILLING_PROVIDER=fake SANDLOOM_ACCEPTED_RISKS=local_storage_in_prod,fake_psp_in_prod ...
```

The microservices profile and `gateway/nginx.conf` are **generated** by `sandloom
add deploy` (run from the repository root): it writes every block between the `# >>>
generated by sandloom add deploy` markers from what the modules provide and
consume, and keeps everything outside them. The same command creates and
updates the profile of an `sandloom new` application
([Split an app into services](../docs/guides/split-into-services.md)); `sandloom
test` checks an application's profile with the invariants below (SANDLOOM-T014).

Both profiles run with `ENVIRONMENT=prod`, so the production validators apply:
`JWT_SECRET`, `TWOFA_ENCRYPTION_KEY` (and `INTERNAL_API_TOKEN` /
`METRICS_TOKEN` when set) must be long and random; placeholders are rejected at
startup.

Comma-separated, newest first, to rotate; keep old keys listed until re-encrypted. Passed to every process that loads identity (migrate, app/identity, worker, beat) |

| `IDENTITY_RPC_PRIVATE_KEY` / `_KEY_ID`, `BILLING_…` | — | **required** (calling services) | each caller's Ed25519 key (`sandloom keys generate --purpose rpc --service <id>`): it signs the caller's COMMAND calls on top of the MAC (`RPC_COMMANDS_REQUIRE_SIGNATURE`, on in prod), so a leaked provider X25519 key cannot forge effects (ADR-0004, KCI). tenancy calls nothing and holds none |
| `RPC_SERVICE_KEYS` | — | **required** (every process) | `{"<service>": {"<kid>": "<PEM>"}}` the callers' Ed25519 public keys |

| `METRICS_TOKEN` | optional | optional | scrape-only credential for `/metrics` (must differ from `INTERNAL_API_TOKEN`); give it to Prometheus instead of the internal token |

`BILLING_*` / `STRIPE_*` are passed to **every** process that loads billing
(migrate, app, worker, beat): each one boots the same composition root, and
billing validates its PSP when the module loads.

### Config parity invariants

Every security/auth-relevant setting lives in the shared env anchor
(`x-common-env` / `x-app-env`), never in a per-service block: a token minted by
identity is verified by every service, so `JWT_*` / token lifetimes must match
(the exceptions are the issuer-only `JWT_PRIVATE_KEY` / `JWT_SECRET` of the
microservices profile, which only identity processes receive —
`test_only_the_issuer_holds_signing_material`);
identity and tenancy both send mail (`NOTIFIER_BACKEND` / `SMTP_*`);
subscription gates evaluate one past-due policy. **`CACHE_URL` is identical for
every service** — a hard invariant: access-token revocation marks, rate-limit
buckets, idempotency keys and the Streams bus live there; a per-service cache
would accept a revoked token everywhere but on the service that revoked it.
`test_deploy_profiles.py` pins all of this (same raw value in every process,
same defaults in both profiles).

### Required modules

Every requested module is **required** (when `MODULE_REQUIRED` is empty) —
listed in `SANDLOOM_MODULES` or filled from the composition root's defaults, in
every profile: if it fails to import or register — e.g. an
`SANDLOOM_MODULES='["sandloom.biling"]'` typo — the process aborts at startup (SANDLOOM-B001)
instead of serving without it. Optionality is explicit:
`define_module(..., optional=True)`, a composition root's
`default_optional_modules`, or `MODULE_REQUIRED` naming the subset that must
load. Independently, `/ready` is 503 whenever modules were
requested but none loaded.

## Migrations (one-shot `migrate` services)

`sandloom migrate upgrade-all --apply` applies the framework's **core chain**
(outbox / audit / consumer inbox — shipped inside the `sandloom` package)
to every database that hosts a module, then each loaded module's **own chain**
to the database it declares. It exits non-zero on failure, and every other
service `depends_on` it with `condition: service_completed_successfully`.

* Monolith: one `migrate` with the full `SANDLOOM_MODULES`.
* Microservices: `migrate-identity`, `migrate-tenancy`, `migrate-billing` —
  each with **that service's** `SANDLOOM_MODULES` and `DATABASE_URL`, so every
  service database gets the core chain + only its own module's tables.
  The databases are created on the first start of the Postgres volume by
  `postgres/init-databases.sh` (`POSTGRES_MULTIPLE_DATABASES`), which also
  creates the `citext` and `pg_trgm` extensions in each. A service added to
  an existing volume later gets its database from its own one-shot
  (`upgrade-all --apply --create-databases` creates a missing database and
  those extensions; the role needs `CREATEDB`).

Extensions: identity's chain runs `CREATE EXTENSION IF NOT EXISTS` for `citext`
and `pg_trgm` (the admin user search index). Both are trusted, so a
non-superuser migration role needs `CREATE` on its database, or a superuser
must create them first (as the init script does). The same applies to the
`multi_tenant_strict` profile; see `docs/operations/operator-reference.md` → Database migrations.

**Concurrent runs.** Each run holds a per-database PostgreSQL advisory lock
for its whole duration, so two `migrate` jobs serialise. The second one waits
at most `--lock-timeout SECONDS` (default `MIGRATION_LOCK_TIMEOUT_SECONDS`,
300) and logs every 5 s who holds the lock — from `pg_locks` +
`pg_stat_activity`:

```
[migrations] waiting for migration lock on postgresql+psycopg2://***@db:5432/sandloom
held by pid 4242 (application_name='<runner>', user='sandloom', client=10.0.3.7,
state='idle', query_start=2026-10-24 08:28:16+00:00, since=…) (5s of 300s)
```

The timeout error names the holder too. Runners connect with
`application_name='sandloom-migrate'` (the kernel's lock name); a role without <!-- stale-ok: runtime application_name -->
`pg_read_all_stats` may not
see another role's session (the message then says so).

Run it manually (any container of the image works):

```bash
docker compose -f deploy/compose/monolith.yml run --rm migrate
docker compose -f deploy/compose/microservices.yml run --rm migrate-billing
```

## Background work (Celery worker + beat)

Workers run the **framework** entrypoint, not a module's:

```bash
celery -A sandloom.core.worker worker --loglevel=INFO
celery -A sandloom.core.worker beat   --loglevel=INFO --schedule=/tmp/celerybeat-schedule
```

`sandloom.core.worker` boots the same composition root as the API
(`SANDLOOM_COMPOSITION_ROOT`, default `sandloom.main`) with the process's `SANDLOOM_MODULES`,
resolves the Celery app through the `taskqueue` capability
(`SANDLOOM_WORKER_TASKQUEUE`, default `default`), imports `<module>.tasks` for every
loaded module and connects each module's `setup_periodic_tasks(sender)` beat
hook. Run **exactly one beat** per broker (a second one stands by — see
"Beat singleton lease" below).

**Sizing.** Celery's own default is one prefork child per *host* core, each a
full copy of the composition root: on a 10-core host a 0.5-CPU / 384 MiB
worker forked 10 children and was OOM-killed in a loop (while the container
still showed "running"). The framework sets `worker_concurrency` from
`WORKER_CONCURRENCY`, else from the container CPU quota capped at 2 (an
explicit `--concurrency` still wins); `WORKER_MAX_MEMORY_PER_CHILD` (KiB) and
`WORKER_MAX_TASKS_PER_CHILD` recycle children. Each child opens its own DB
pool (`WORKER_DB_POOL_SIZE` / `WORKER_DB_MAX_OVERFLOW`). Memory: ~150 MiB for
the main process + one child; the profiles give workers 512 MiB.

**Liveness.** The worker's own timer touches `/tmp/sandloom-worker-heartbeat`
(`WORKER_HEARTBEAT_FILE`) every 10 s; `python -m sandloom.core.worker healthcheck`
exits non-zero when it is missing or older than 60 s. It boots nothing (no
broker round-trip, no second app copy inside the memory limit — unlike
`celery inspect ping`), so it is the compose `healthcheck` and the k8s
`livenessProbe.exec` command for workers.

In the microservices profile `identity` (housekeeping) and `billing` (the
operation-intent reconciler `reconcile_operation_intents`, every 5 min, and the
orphan payment-state purge) ship periodic tasks, hence `identity-worker` /
`identity-beat` and `billing-worker` / `billing-beat`. Each service has its own
`BROKER_URL` (Redis db 2/3/4) so a task can never be picked up by a service that
does not load its module.

**One scheduler per task set.** A beat schedules exactly the
`setup_periodic_tasks` of the modules in ITS `SANDLOOM_MODULES`, onto its own
service's broker; the worker of the same service (same env anchor, same broker)
is the only consumer. So there is exactly one beat per broker and per module
with periodic tasks — no schedule runs twice, none is missing.
`test_deploy_profiles.py::test_every_periodic_task_set_has_exactly_one_beat`
pins it for both profiles (in the monolith the single `beat` loads every
module). To give another service a worker, copy the pair with that service's
env anchor.

**Beat singleton lease.** The compose files declare one beat per task set; a
second beat started by mistake (a scaled-up replica, a manual `celery beat`
left running, a k8s rollout that overlaps old and new pods) would send every
periodic task twice. The framework beat therefore schedules only while it
holds a lease in the cache (`sandloom.core.beat_lease`):

* the key is `sandloom:beat:lease:<scope>`, the scope a digest of the broker URL,
  the taskqueue instance and the sorted `SANDLOOM_MODULES` — replicas of one
  service share it, different services never suppress each other
  (`BEAT_LEASE_NAME` pins an explicit scope);
* acquire = `SET NX` with a TTL (`BEAT_LEASE_TTL_SECONDS`, default 30) of a
  fenced token `<fence>:<host>:<pid>:<nonce>` (`<fence>` from an `INCR`, so
  every takeover gets a larger number); renew every TTL/3 with a
  compare-and-set on that token;
* a second beat logs `[beat] standby: another beat holds lease …` and sends
  nothing; it takes over within TTL + TTL/3 after the holder dies, at once
  after a clean shutdown (the holder deletes its own token);
* a holder whose token was replaced stops scheduling immediately; on a cache
  outage it keeps scheduling only until its local lease deadline, then stands
  by until it can write again;
* the lease lives in `BEAT_LEASE_CACHE_INSTANCE` (default `default`, the
  shared `CACHE_URL`) and needs the `cas` feature (Redis); with a cache
  without it beat refuses to start. The lease is always on (there is no
  switch to turn it off).

The lease wraps whatever scheduler beat runs (`-S …` included) and applies to
`worker -B` too. A takeover starts from the new beat's own schedule file, so a
task whose period elapsed during the failover runs once on takeover.

## How the split works

1. **Module loading.** `sandloom.core.loader.plugin_loader` reads `SANDLOOM_MODULES` (JSON
   list) and calls each module's `register(core)`. Only the listed modules'
   routes, event schemas, and services exist in that process.
   `MODULE_WHITELIST` / `MODULE_BLACKLIST` further filter the list.
2. **Async communication** rides the durable Redis Streams bus in both
   profiles (`EVENT_BUS_BACKEND=auto` resolves to `streams` in prod; the
   microservices profile pins `streams` explicitly) on the shared `CACHE_URL`;
   each service's transactional outbox lives in its own database and its relay
   (one gunicorn worker per container) dispatches it. Versioned channels
   (`identity.user_registered.v1`, …) keep producers and consumers decoupled.
3. **Sync cross-module contracts** go through the core service registry
   (e.g. billing resolves `tenancy.membership.v1`). A co-deployed provider is
   used in-process; otherwise `SERVICE_BINDINGS` (JSON
   `{"<contract>": {"base_url": "http://<service>:2222", "service_id": "<service>"}}`
   — `service_id` is required and pins the provider) makes
   `core.get_service()` return a generated internal RPC proxy whose calls are
   MACed with the caller/provider pair key (ADR-0004); the provider
   allows it only the contracts in `RPC_ALLOWED_CALLS[<caller>]`, so when you
   add a binding, add it there too (the caller refuses to start otherwise).
   Each service binds EXACTLY the contracts its
   modules declare in `ModuleDescriptor.consumes` and do not provide (checked
   at startup: a missing required one aborts boot, a missing optional one
   warns): billing binds `tenancy.membership.v1` → `tenancy`; tenancy binds
   nothing. Access facts owned elsewhere are consumed through the owner's
   `<owner>.facts.v1` (e.g. `billing.facts.v1` for `Entitled(...)` /
   `Subscribed()` outside billing). Identity is the token issuer, so it binds
   only the claims contracts of the modules deployed elsewhere:
   `tenancy.claims.v1` (critical — no token without `tenant_ids`) and
   `billing.claims.v1` (`"critical": false`, matching billing's contributor —
   a billing outage is recorded in `claims_sources_failed`). With neither a
   local provider nor a binding, consumers degrade explicitly (403/404/501).
   `SERVICE_BINDINGS` is validated at startup: allowed keys are `base_url`
   (or `url`, absolute `http(s)://`), `timeout_seconds`, `critical`,
   `required` and `service_id` — the provider's `RPC_SERVICE_ID`, REQUIRED:
   every call's pair key derives from it and its responses must be keyed by
   it; anything else (a `"requried"` typo) is an error, and a caller without
   its own X25519 key refuses to start.
   A peer that is DOWN fails only the calls that need it
   (`RemoteServiceUnavailable` → 503 at call time); see *Probes*.
4. **Routing.** The gateway (`gateway/nginx.conf`) maps path prefixes to
   services. Adding a module = adding a `location` block
   (`test_deploy_profiles.py` checks every module route reaches its owning
   service and that `/_sandloom`, `/diagnostics`, `/metrics`, `/ready`, … are not
   routed). The gateway re-resolves service names through Docker DNS
   (`resolver 127.0.0.11 valid=10s` + `server <svc>:2222 resolve`, nginx ≥
   1.27.3), so a recreated container is reached without restarting nginx;
   `proxy_connect_timeout 2s` makes a down service answer 502/504 within ~2 s
   instead of hanging; `client_max_body_size 50m` matches the app's
   `MAX_UPLOAD_SIZE_BYTES` default (raise both together).

## Probes (liveness vs readiness)

| Endpoint | Meaning | Use as |
| --- | --- | --- |
| `/health/simple` | process is up | k8s `livenessProbe` (recommended), compose healthcheck |
| `/health` | **local** infra (db, cache, storage, event bus, named instances, module checks) | dependency diagnostics; do not use as liveness |
| `/ready` | `/health` + required modules loaded + ≥ 1 module when any was requested + required consumers subscribed + required peers reachable + every reachable bound provider compatible with this release's contract snapshot | k8s `readinessProbe` |

Remote peers (`SERVICE_BINDINGS`) are **never** part of `/health`: restarting
a service cannot fix its peer, and probing peers there turned one stopped
service into a restart cascade. They affect `/ready` only for bindings marked
`"required": true` (default false) — otherwise a stopped billing drained
identity and tenancy from the load balancer, and mutual bindings
(tenancy ↔ billing) deadlocked a cold start. Required probes run concurrently,
each capped at `SERVICE_PROBE_TIMEOUT_SECONDS` (default 1 s), and are
authenticated like calls (pair MAC). `/diagnostics/services`
(internal token) reports the reachability of every binding.

A database, Redis or connection-pool outage must not restart every application
replica. Use `/health/simple` for liveness and `/ready` for traffic admission;
an unsuccessful `/health` is a diagnostic signal, not proof that restarting the
process will repair its dependencies.

### Multiworker metrics and shutdown

The shipped Gunicorn configuration owns a fresh Prometheus multiprocess
directory for each master and sets `PROMETHEUS_MULTIPROC_DIR` **before** workers
import the application. `/metrics` aggregates all workers in that directory.
Counter history survives worker recycling; live gauges drop exited workers.
Do not share a directory between masters or replicas. An explicitly configured
directory is locked and its stale `*.db` files are cleared at master startup;
other files are preserved. `preload_app` is refused because importing metrics
before the environment is set would silently select process-local storage.
SIGHUP retains the master's directory. Scrape each replica separately and sum
counters in Prometheus across replicas as usual.

`SHUTDOWN_BUDGET_SECONDS` (default 30 s) covers post-commit drain, relay,
consumers, module/infra teardown and tracing flush together. Each phase shares
the same monotonic deadline. Gunicorn's default graceful timeout is 45 s and
must exceed the shutdown budget; the compose profiles allow 60 s before
SIGKILL. Increase all three together when long requests need more drain time.
Cancellation-resistant code cannot be forcibly stopped inside a Python process;
the supervisor's final grace deadline remains the hard limit, and durable
outbox/inbox state is recovered by the next process. Test shutdown under the
actual deployment supervisor before declaring its release artifact qualified.

For Kubernetes, use `terminationGracePeriodSeconds: 60` or longer, allow any
`preStop` drain delay **in addition** to request drain and the shutdown budget,
and remove the pod from readiness before traffic is terminated. A `preStop`
delay consumes the same Kubernetes grace period; it does not extend it.

Access logging is off by default (`GUNICORN_ACCESSLOG` unset). To opt in, set
`GUNICORN_ACCESSLOG=-`; worker access handlers use JSON/redaction and omit query
values. HTTP RED metrics remain available with access logs disabled. Behind a
load balancer, set `TRUST_PROXY_HEADERS=true` and enumerate only its trusted
addresses in `TRUSTED_PROXY_IPS`; enabling trust without a restricted proxy
allowlist would allow clients to forge rate-limit identity.

Both demonstration profiles explicitly opt into local object storage through
the accepted risk `local_storage_in_prod` (their default
`SANDLOOM_ACCEPTED_RISKS`; keep it when overriding the list) and mount the same
persistent `appdata` volume at `/app/data` in their application services and
workers. This supports their single-host topology only. For multiple hosts, use a shared filesystem
with suitable durability/access controls or an object-store driver; separate
local volumes on different hosts are not a shared object store. Environment
secrets and inline demonstration database credentials in these profiles are
for the demo topology; use the documented `SECRETS_DIR` file mechanism and
deployment-specific credentials for production.

The behaviour is pinned by tests:
`src/sandloom/core/tests/test_module_subset.py` proves any module subset
boots standalone with exactly its own routes;
`src/sandloom/core/tests/test_deploy_profiles.py` validates every process
environment in both profiles against the production settings.

## Rolling upgrades: contract compatibility

During a rolling upgrade a caller built from release N+1 talks to a provider
still on release N (or the reverse). Sync contracts are therefore checked as
versioned interfaces, not assumed to match:

- **Snapshots.** Every module ships `contracts.snapshot.json` next to its
  `__init__.py`: the describe document (methods, parameter / return type
  descriptors incl. model fields, read/command kind, idempotency key) of each
  contract it provides. Regenerate with `sandloom contracts snapshot --write`;
  `sandloom contracts snapshot --check` (and the framework test
  `test_committed_module_snapshots_match_registered_contracts`) fails CI when a
  snapshot is stale, so every contract change shows up as a reviewed diff.
- **CI breaking-change gate.** `sandloom contracts check --against <snapshot of the
  released version>` (default `--as provider`) exits 1 when this build breaks
  callers that expect the released contract: a removed method or parameter, a
  newly required parameter, a parameter that became required / keyword-only /
  positional-only or moved position, a changed kind or idempotency key, a
  parameter type the provider no longer accepts, a result type the caller
  cannot accept, a required model field added (argument) or removed (result).
  Additive changes pass: new methods, new optional parameters, optional model
  fields, widened parameter types, narrowed result types.
- **Pre-deploy.** `sandloom contracts check --against http://<provider>:2222`
  (default `--as consumer`, needs the internal token) compares this build's
  expectations with a RUNNING provider.
- **Runtime.** With `CONTRACT_COMPAT_CHECK=ready` (default) a caller resolves
  the expected shape of each remote-bound contract from the provider module's
  snapshot in its own image (the single framework image carries every module;
  an image built from the per-module wheels must set `CONTRACT_SNAPSHOT_PATHS`
  — a binding without any snapshot is logged at startup as unchecked) and
  compares it
  with the provider's live describe document (`GET /_sandloom/rpc/<contract>`):
  an incompatible provider fails `/ready` with a `contract_incompatible`
  diagnostic naming each break — for every binding with a snapshot, `required`
  or not (an unreachable non-required peer still never fails `/ready`), and is
  logged at startup. `strict` also aborts startup when a reachable provider is
  incompatible; `off` disables the check. A peer that publishes no field
  information (pre-snapshot releases) yields warnings (`contracts_unverified`),
  not failures. Narrow the check to what a module really calls with
  `ContractRequirement("billing.credits.v1", methods=("spend",))`.
- **Order of a rolling upgrade.** Ship additive contract changes first
  (provider before callers); a breaking change is a new contract version
  (`.v2` registered next to `.v1`) until no caller binds `.v1` any more.

## Gateway and client IPs (X-Forwarded-For)

* **Monolith:** clients connect to the app directly, so
  `TRUST_PROXY_HEADERS=false` — a client-supplied `X-Forwarded-For` is
  ignored (otherwise any client could choose its own rate-limit bucket).
* **Microservices:** every request passes the nginx gateway, which has a fixed
  address (`SANDLOOM_GATEWAY_IP`, default `172.28.0.10` in `SANDLOOM_SUBNET`) and *appends* the peer to `X-Forwarded-For`
  (`$proxy_add_x_forwarded_for`). Services set `TRUST_PROXY_HEADERS=true` and
  `TRUSTED_PROXY_IPS=["172.28.0.10/32"]`: the app walks XFF right-to-left and
  stops at the first untrusted hop, so the client-controlled left part is never
  believed. The gateway also blanks `X-Internal-Token`, so the internal
  credential can never be supplied from outside.
* Behind another load balancer, add its CIDR to `TRUSTED_PROXY_IPS` (and keep
  the gateway's).

## Runtime restrictions

Application containers (HTTP, migrations, workers and beat) run as UID 10001
with `read_only: true`, `cap_drop: [ALL]` and
`security_opt: ["no-new-privileges:true"]`. These options belong to the
`x-app-runtime` anchor; database, Redis and gateway images keep their own
entrypoint requirements. The generated project and split profiles use the same
application boundary.

Older split profiles retain their operator-owned sections outside generated
markers when refreshed. Adopt the `x-app-runtime`, HTTP and migration anchors
from the current template before claiming the new restrictions for such a
profile; refresh remains valid with its previous `service-runtime` anchor.

Only `/app/data` (persistent storage) and `/tmp` (private tmpfs) are writable.
The tmpfs is bounded to **128 MiB**, owned by UID/GID 10001, and mounted with
`noexec,nosuid,nodev`. Gunicorn metrics/worker files, the Celery heartbeat and
beat schedule use it. It is cleared on container recreation. Large temporary
workloads need an explicitly sized scratch mount; do not make the root writable.
Export backups to a dedicated writable mount or `/app/data`, not the working
directory. Change permissions/ownership of an existing storage volume before
starting the restricted process if it was created by a different UID.

The image removes APT, its runtime library, mount/account administration tools
and SUID/SGID file bits after creating the application user. It refuses to
remove essential or protected packages, never uses force-removal or autoremove,
and preserves Debian package metadata. Build dependencies belong in the builder;
changes to system packages require rebuilding the image. The shipped hardener
is reviewed for the pinned Debian 13 base; a different base needs review.

The Docker CI job runs `tools/checks/runtime_inventory.py --enforce` **inside
the actual image**. It checks kernel capabilities and `NoNewPrivs`, rejects
SUID/SGID files, tests successful scratch/storage writes, rejects an application
root write, and proves an executable cannot run from `/tmp`. Its
`runtime-security-inventory` artifact contains package/component evidence.
Static tests check the application services in every shipped/generated profile.

For other orchestrators, preserve the same restrictions: for example Kubernetes
`runAsNonRoot`, UID 10001, `allowPrivilegeEscalation: false`, dropped capabilities,
`readOnlyRootFilesystem` and explicit scratch/storage mounts. Running an image
without the profile does not automatically apply these runtime controls.

The [Debian review](../design/security/debian-runtime-2026-10-31.md) and
[supply-chain guide](../docs/contributing/supply-chain.md#runtime-container-scope)
distinguish removed components, inapplicable findings, mitigations and unresolved
vendor issues. Restrictions do not turn unresolved CVEs into patched libraries.

## Sizing

The image installs the `sandloom[fast]` extra (hiredis reply parser,
jsonschema-rs payload validation); the framework falls back to the pure-Python
engines without it.

The image runs gunicorn with `sandloom.core.cli.gunicorn_conf`: the worker count
honours the container CPU quota (default `min(2*cpus+1, 4)`; a non-empty
`WEB_CONCURRENCY` overrides it), and the master elects exactly **one** worker
per container to run the outbox relay.

Workers are `uvicorn_worker.UvicornWorker` on **uvloop + httptools** (from
`uvicorn[standard]`); each logs what it booted with, e.g.
`sandloom worker booted: loop=uvloop http=httptools keepalive=75s`.
`GUNICORN_KEEPALIVE` (default **75 s**, uvicorn's `timeout_keep_alive`) must
exceed the idle timeout of whatever proxies to the app — AWS ALB 60 s, nginx
`keepalive_timeout` 60–75 s, GCP LB 600 s (raise it there). If the app closes
an idle upstream connection first, the balancer can send a request on a socket
the app is closing and the client gets a sporadic 502.

**Postgres connection budget.** Every process holds two pools: the request
pool (`DB_POOL_SIZE + DB_MAX_OVERFLOW`) and the dedicated contract pool
(`CONTRACT_DB_POOL_SIZE + CONTRACT_DB_MAX_OVERFLOW`; in-process contract calls
and claims contributors use it so they never starve the request pool). At its
maximum a container holds `processes × (both pools)`, where processes is
`WEB_CONCURRENCY` for an HTTP service and `WORKER_CONCURRENCY` (default: CPU
quota, max 2) for a worker. The monolith app sets the contract pool to 3 + 3
(every cross-module call is in-process there, concurrently with the request's
own connection); workers and the microservices (whose cross-module calls go
over RPC) keep 1 + 2. Both profiles set the server's `max_connections`
explicitly to **150** (`db.command`):

| Profile | Process | Count | Request pool | Contract pool | Connections |
| --- | --- | --- | --- | --- | --- |
| monolith | app | 3 | 10 + 10 | 3 + 3 | 78 |
| | worker | 2 | 2 + 2 | 1 + 2 | 14 |
| | beat | 1 | 1 + 0 | 1 + 0 | 2 |
| | migrate (NullPool, one-shot) | 1 | | | ≤ 2 |
| | **total** | | | | **96** |
| microservices | identity / tenancy / billing | 3 × 2 | 5 + 5 | 1 + 2 | 78 |
| | identity-worker | 2 | 2 + 2 | 1 + 2 | 14 |
| | identity-beat | 1 | 1 + 0 | 1 + 0 | 2 |
| | billing-worker (`WORKER_CONCURRENCY=1`) | 1 | 2 + 2 | 1 + 2 | 7 |
| | billing-beat | 1 | 1 + 0 | 1 + 0 | 2 |
| | 3 migrate one-shots | 3 | | | ≤ 6 |
| | **total** | | | | **109** |

All three microservice databases live on one Postgres server, so the limit is
server-wide; per database at peak: `sandloom_identity` 26 + 14 + 2 + 2 = 44,
`sandloom_tenancy` 26 + 2 = 28, `sandloom_billing` 26 + 7 + 2 + 2 = 37. The billing
worker runs one prefork child (`BILLING_WORKER_CONCURRENCY`, default 1): its
tasks are light and periodic, so a second child would only hold 7 idle
connections.

`test_deploy_profiles` recomputes this budget from the compose files and
requires it (plus 10 connections of admin headroom) to fit `max_connections`.
Raising `WEB_CONCURRENCY`, a pool size or the number of services means raising
`max_connections` (or putting PgBouncer in front of Postgres) too — the stock
default of 100 is already exhausted by the microservices profile at peak.

## Checklist for extracting a module into its own service

`sandloom add deploy <module>... --service <name>` does steps 1–5 for you, in the
framework and in an `sandloom new` application: the env anchor (modules, database,
broker DB, RPC identity and keys, the bindings of what they consume), the
migrate one-shot and HTTP service, the database in
`POSTGRES_MULTIPLE_DATABASES` (and a `max_connections` that fits the budget),
bindings in the services that consume its contracts, the re-derived
`RPC_ALLOWED_CALLS`, an nginx upstream plus the locations of each route
prefix, bounded at its segment (`location = /shop` and `location /shop/`, so
`/shopping` stays with a root-level `/{slug}`; root-level routes, `/` and
`/{slug}`, get `location = /` and the catch-all),
and the worker / beat pair. It is idempotent and incremental (a module added
to an existing service, `--refresh` after a code change); hand edits inside
its generated blocks are refused with a diff. Then generate the keys (`sandloom
keys generate --purpose rpc-dh --service <name>`, and `--purpose rpc` when it
calls other services; `sandloom keys dev-env` for development) and run `sandloom add
deploy --check` (the invariants, and every service booted alone). A module
the microservices profile does not deploy is a warning in
`test_deploy_profiles.py` (SANDLOOM-T003), never a failure: deploying it is a
topology decision, not part of a feature. The checklist below is what it
writes.

1. Add an env anchor with its own `SANDLOOM_MODULES: '["sandloom.<module>"]'`,
   `DATABASE_URL` (add the database to `POSTGRES_MULTIPLE_DATABASES`) and
   `BROKER_URL`.
2. Add a `migrate-<module>` one-shot with that anchor and make the service
   depend on it (`service_completed_successfully`).
   **Existing data does not move by itself**: steps 1–5 change code and
   topology only — step 6 (`sandloom migrate extract-module`, runbook below) moves
   the data.
3. Declare the contracts it calls in `ModuleDescriptor.consumes` and bind
   exactly those (not provided locally) in its `SERVICE_BINDINGS` (and bind its
   own contracts in the services that consume them). If it registers a
   claims contributor, bind its `<module>.claims.v1` in the token issuer's
   (identity's) `SERVICE_BINDINGS`, with `"critical": false` iff its
   contributor is non-critical (`test_deploy_profiles.py` enforces this).
4. Add the module's path prefixes to the gateway.
5. If the module ships `tasks.py`, add a worker/beat pair with the same anchor
   (exactly one beat per service broker; recompute the connection budget).
6. Move the module's EXISTING data — see the runbook below. A new
   deployment with no data skips it.

## Runbook: moving a module's data out of the monolith database

Steps 1–5 change topology; a running SaaS also has the module's rows in the
monolith database. `sandloom migrate extract-module` moves them **offline, in a
maintenance window** (the module's writers are stopped; other modules keep
serving). Run it with the MONOLITH's configuration (its `SANDLOOM_MODULES` must
load the module; `--from`/`--to` take an instance name or a URL):

```bash
# 0. Plan (dry-run, the default — writes nothing anywhere):
sandloom migrate extract-module billing --from default --to "$BILLING_DATABASE_URL"
# 1. Stop every writer of the module: the app replicas that load it, its
#    Celery worker/beat, its consumers. (The rest of the monolith may run —
#    but nothing may write billing tables or publish billing.* events.)
# 2. Extract (fence -> migrate target -> copy -> verify -> hand off events):
sandloom migrate extract-module billing --from default --to "$BILLING_DATABASE_URL" \
    --apply --i-have-stopped-writes
# 3. Optional re-check at any time (row counts + checksums vs the manifest):
sandloom migrate extract-module billing --from default --to "$BILLING_DATABASE_URL" --verify
# 4. Cut over: start the billing service (its own DATABASE_URL, same CACHE_URL /
#    bus / JWT settings), remove sandloom_billing from the monolith's SANDLOOM_MODULES,
#    add the SERVICE_BINDINGS (checklist step 3), switch the gateway routes.
# 5. Later, once the service has run cleanly — cleanup (separate, explicit):
sandloom migrate extract-module billing --from default --to "$BILLING_DATABASE_URL" \
    --drop-source --apply --i-have-stopped-writes
```

What `--apply` does, in order (every step is idempotent — after a crash or a
refusal fix the cause and re-run the SAME command; it resumes):

1. **Preflight**: the source chain must be at the code's head, every module
   table present, no foreign key leaving the module, and RLS-protected tables
   need a superuser / `BYPASSRLS` role (else the copy would see one tenant).
2. **Fence**: statement-level triggers make every module table read-only and a
   row trigger refuses new `outbox_messages` rows on the module's channels
   (SQLSTATE `25006`). Installing it takes the table locks under
   `--lock-timeout-ms` (default 5 s): a live writer makes the run fail with
   "the module still has writers" instead of racing the copy. The fence stays
   after the run — the source copy is now stale, a write to it would be lost.
3. **Target schema**: extensions the module's columns use (e.g. `citext`),
   the core chain and the module's own chain, at head.
4. **Copy**: the module's tables (its mapped models + the `<key>_` prefix) in
   FK order with `COPY`, one transaction per table that also writes a manifest
   row (`sandloom_module_extractions` in the target: row count + checksum). A
   table is verified (count + content checksum computed by PostgreSQL on both
   sides) before it commits. A re-run skips tables whose manifest matches the
   fenced source; a non-empty target table without a manifest is refused,
   never overwritten.
5. **Sequences** (`serial` / identity) are set to the source's position.
6. **Core-infra rows**, by ownership rule:

   | table | rows that belong to the module | what happens |
   |---|---|---|
   | `outbox_messages` | channel `<module>.…`, not delivered (pending + dead) | copied with the SAME id (stable envelope id), then marked delivered in the source with `last_error = "sandloom migrate extract-module: handed off to url:…"` — the new service's relay sends them, the old database never re-sends them. Dead rows stay dead in the target (`sandloom outbox requeue` there). Delivered rows are history and stay. |
   | `consumer_inbox` | consumer `<pkg>:<name>` (its consumer groups), its explicit `group=` ids, `<module>@…` | copied, so a redelivery after the move is still deduplicated; deleted from the source only by `--drop-source` |
   | `audit_log` | action `<module>.…` | copied; the source keeps its copy (audit is never deleted by this tool) |
   | `contract_command_log` | contract `<contract>.<method>` of every contract the module registered (and `<module>.…`) | copied, so a retried command that completed before the move replays its stored result in the new service instead of running twice; deleted from the source only by `--drop-source` |

7. **Verify + manifest**: everything re-checked; the completion marker is
   written; then Streams **consumer-group ownership** is transferred: every
   `sandloom:group-owner:<stream>:<group>` owned by the module on the source
   database is re-pointed (compare-and-set) to the target database, so the
   new service claims the group without a conflict, continues from the
   group's position (pending entries of the dead monolith consumers are
   reclaimed by `XAUTOCLAIM` and deduplicated by the copied inbox), and a
   stale monolith that still loads the module is REFUSED at startup. The
   identity is computed from `--to`; pass `--target-identity-url` /
   `--source-identity-url` when the services reach the databases under other
   host names. `--no-transfer-groups` skips it (then `sandloom streams
   release-group` by hand).

Rollback before the cutover: `--unfence --apply` makes the source writable
again (refused after the extraction completed unless `--force`: the new
service may already have taken writes the source does not have).
`--drop-source` requires the completed manifest, re-checks that the fenced
source still matches it and refuses while undelivered module events remain;
it drops the module tables and `alembic_version_<key>`, deletes the module's
inbox claims, and keeps audit rows, handed-off outbox rows and the outbox
fence.

Proven by `tests/extraction/test_extraction_e2e.py` (opt-in:
`SANDLOOM_EXTRACTION_E2E=1 uv run pytest tests/extraction --no-cov`, CI job
`extraction-e2e`, manual / nightly): a monolith with users, orgs, members,
invitations, subscriptions, credits and in-flight events is extracted
(tenancy + billing) and restarted as three services; every recorded answer
(status + JSON body, same ids) is identical, tables match by checksum, in-flight events are relayed exactly
once by the new owner, and a credit-spend workload survives a SIGKILL of the
billing service (no lost or double-spent credit, one ledger row and one event
per spend). `src/sandloom/core/tests/test_module_extraction.py` covers the fence,
crash + resume, refusals, drop-source / unfence and the group transfer.

### Not covered: online (zero-downtime) extraction — future work

The window lasts as long as the copy (roughly the module's data size at
`COPY` speed) plus the cutover; the module is unavailable for writes during
it (other modules keep serving). Two designs for an online mode:

- **CDC-based (preferred)**: logical replication of the module's tables
  (`CREATE PUBLICATION … FOR TABLE <module tables>` in the source,
  subscription in the target after the same schema migration), initial sync
  + streaming catch-up while the monolith keeps writing; cutover = fence
  (seconds), wait until the subscription's LSN reaches the source's, hand off
  outbox/inbox rows (they are not replicated), stop the subscription,
  `setval` the sequences (logical replication does not carry them), switch
  traffic. Needs `wal_level=logical` and a replication role; the outbox
  hand-off and group transfer above are reused unchanged.
- **Dual-write**: the module writes both databases behind a feature flag
  (old = source of truth), a backfill job copies history, a verifier compares
  checksums per tenant, then the flag flips the source of truth. Works without
  replication privileges but needs application support in every write path
  and a reconciliation story for partial dual-writes — heavier for the
  framework than CDC.

Neither is implemented; until then plan a maintenance window per module.

## Production hardening notes

- A shared multi-tenant SaaS should run with
  `PRODUCTION_PROFILE=multi_tenant_strict`: the process then refuses to start
  unless Row-Level Security is on for every database (and covers every tenant
  table), revocation fails closed, security-critical cache state has its own
  non-evicting Redis (`SECURITY_CACHE_INSTANCE`) and, when split, the contract
  compatibility check is on. The full contract, the Redis HA recommendations
  and the mapping of named cache instances are in
  `docs/reference/security-model.md` → *Production profile*. The compose
  profiles in this directory are demo stacks and do NOT meet it (one Redis,
  no RLS roles).

- Generate strong secrets; the monolith's processes share `JWT_SECRET`; in
  the microservices profile only identity holds `JWT_PRIVATE_KEY` /
  `JWT_SECRET` and every service shares `JWT_PUBLIC_KEYS` (rotation runbook:
  `docs/reference/security-model.md`); every service holds its own X25519
  `RPC_DH_PRIVATE_KEY` — it authenticates that service's RPC calls, so it
  is as sensitive as a signing key — and shares the public
  `RPC_SERVICE_DH_KEYS` (rotate per service, independently: ADR-0004); all services share
  `INTERNAL_API_TOKEN` (ops endpoints only); every identity process shares `TWOFA_ENCRYPTION_KEY`
  (losing it makes enrolled TOTP secrets undecryptable — back it up).
- Put TLS on the gateway (terminate at nginx or an upstream LB).
- `/metrics` (Prometheus; `METRICS_TOKEN` or `INTERNAL_API_TOKEN`) and
  `/health`, `/ready` (k8s probe contract: 503 when degraded) are exposed by
  every service.
- Redis persists the Streams event log (`appendonly yes` + a volume,
  `maxmemory-policy noeviction`) in **both** profiles — in prod the monolith
  also runs its bus on Redis Streams, so an unpersisted Redis lost pending
  events on restart. Cache and bus share one Redis here; splitting them (a
  volatile cache with an eviction policy, a persistent `noeviction` bus) is
  optional but recommended at scale. Back up Postgres per service database.

### Separate idempotency Redis (opt-in)

By default `idempotency_guard` reservations / replay records and task-enqueue
dedupe records live in the security cache (`SECURITY_CACHE_INSTANCE`) next to
the revocation marks every authenticated request reads. On a security Redis
that fsyncs every write (`appendfsync always`, single-threaded), the
idempotency `SET NX` fsyncs queue those reads and dominate the p99 of guarded
writes (`docs/design/write-login-profile-2026-10-22.md`). Moving the records
to their own, **equally durable** Redis removes that contention without
weakening any guarantee:

```yaml
# shared env (identical in EVERY process)
INFRA: '{"cache": {"security": {...}, "idempotency": {"driver": "redis", "url": "redis://idempotency-redis:6379/0"}}}'
IDEMPOTENCY_CACHE_INSTANCE: idempotency

# service
idempotency-redis:
  image: redis:7
  command: ["redis-server", "--appendonly", "yes", "--appendfsync", "always",
            "--maxmemory", "256mb", "--maxmemory-policy", "noeviction"]
  volumes: [idempotencyredisdata:/data]
```

Both compose profiles carry this block commented out. Give it the same
persistence, `noeviction`, backups and HA as the security Redis — never
`appendfsync everysec` (a lost reservation re-executes a mutation).
Revocation marks, blocks and the RPC replay guard stay in the security cache;
`fail_closed=True` guards answer `503` when the idempotency Redis is down,
exactly as they did for the security one. Under
`PRODUCTION_PROFILE=multi_tenant_strict` the instance must be declared in
`INFRA["cache"]` on a Redis server other than the default cache's (attested
at startup); sharing the security Redis's server only warns (it removes no
contention). Leave it unset to keep today's behaviour.

## Optional admin UI

The [admin application](../admin/README.md) ships separately from the backend.
Add `docker-compose.admin.yml` to either profile and enable `--profile admin`.
The default upstream is `http://app:2222`; for the split profile set
`SANDLOOM_ADMIN_API_UPSTREAM=http://gateway:8080`. The admin port binds to loopback
by default. Configure TLS, the trusted forwarding chain and existing backend
secrets for the deployment as usual. The UI does not expose internal endpoints
or grant platform/tenant privileges.
