# Split modules into services

The code does not change; the topology does. One command does the wiring, in
an `sandloom new` app (from its root) and in the framework (from the repository root). The
guide is `docs/operate/split-into-services.md`; inside an app, run
`uv run sandloom docs recipe split`.

## Steps

1. **Choose the services.** Each module runs in exactly one service; a
   service may hold several modules. Bundled modules (identity, tenancy,
   billing) can each be their own service.
2. **Write the split.** Run one command per service:

   ```bash
   uv run sandloom add deploy identity                      # service "identity"
   uv run sandloom add deploy tenancy
   uv run sandloom add deploy billing
   uv run sandloom add deploy catalog enrollment --service academy
   ```

   - The first run creates `deploy/compose/microservices.yml`,
     `deploy/gateway/nginx.conf` and `deploy/postgres/init-databases.sh` from
     the package's templates. An app ships only the monolith profile, so
     never hand-write these files.
   - Every run re-derives, from what the modules provide and consume:
     - per service: an env anchor, its own database, a migrate one-shot,
       its RPC keys, a worker for `tasks.py` and one beat for periodic tasks;
     - `SERVICE_BINDINGS`, including the issuer's remote `<m>.claims.v1`;
     - `RPC_ALLOWED_CALLS`, the databases and `max_connections`;
     - the gateway routes. The gateway never routes `/_sandloom`, `/diagnostics`
       or `/metrics`.
   - The same command again changes nothing. A new module in an existing
     service: `sandloom add deploy <m> --service <svc>`. After a code change (a
     new consumed contract, a route prefix): `sandloom add deploy --refresh`.
3. **Hand edits.** The command owns only the blocks between the
   `# >>> generated by sandloom add deploy` and `# <<<` markers. Put your
   settings outside them, or in a compose override file. An edit inside a
   block makes the next run refuse with a diff (`--force` overwrites it).
   Never edit the bindings or routes by hand: rerun the command.
4. **Keys.**
   - Development and CI only: `uv run sandloom keys dev-env --out
     deploy/.env.microservices`, then `docker compose --env-file
     deploy/.env.microservices -f deploy/compose/microservices.yml up
     --build`.
   - Production: `sandloom keys generate` (the JWT pair, issuer only), plus `sandloom
     keys generate --purpose rpc --service <caller>` or `--purpose rpc-dh
     --service <provider>`, into a secret store. Each `${VAR:?...}` in the
     profile names its command.
   - Only the token issuer holds `JWT_PRIVATE_KEY` / `JWT_SECRET`.
5. **Existing data:** skill `sandloom-extract-module`. A new deployment skips it.

## Checks (from the project root)

```bash
uv run sandloom add deploy --check   # invariants (SANDLOOM-T014) + every service boots alone
uv run sandloom test                 # schema & deploy checks the profile too
```

The framework also has `src/sandloom/core/tests/test_deploy_profiles.py`, the
split conformance matrix (`tests/split_conformance`, slow) and CI's
`microservices-smoke`. The CI job `app-split` (`tools/smoke/split_check.py`,
`--smoke` for the real stack) splits a fresh `sandloom new` app. Unbound
optional contracts must degrade explicitly (404, 501 or 503), never with a
500.
