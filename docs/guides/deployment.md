# Deployment

Sandloom is a **configurable monolith**: the same codebase and the same Docker image
deploy either as a single process or as a set of services. The split is pure
configuration — `SANDLOOM_MODULES` tells each process which modules to load.

## Profiles

The authoritative, up-to-date description of both compose profiles — required
variables, sizing, gateway/IP trust, the extraction checklist — is
[`deploy/README.md`](https://github.com/Sandloom-dev/sandloom/blob/main/deploy/README.md).
In short:

| Profile | File | Topology |
| --- | --- | --- |
| Monolith | `deploy/compose/monolith.yml` | `migrate` → `app` (all modules, `:2222`) + `worker` + `beat`; one Postgres DB; Redis |
| Microservices | `deploy/compose/microservices.yml` | nginx gateway `:8080` → `identity` / `tenancy` / `billing`, each with its **own database** and its own `migrate-<service>` one-shot; `identity-worker` + `identity-beat`; Redis (Streams bus) |

Both profiles run with `ENVIRONMENT=prod`, so the production validators apply
and these variables are required:

| Variable | Monolith | Microservices |
| --- | --- | --- |
| `JWT_SECRET` | required | required (shared by every process) |
| `TWOFA_ENCRYPTION_KEY` | required | required by every identity process |
| `BILLING_PROVIDER` | required: `stripe` (+ `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`) or `fake` with `SANDLOOM_ACCEPTED_RISKS` listing `fake_psp_in_prod` (demo only) | same |
| `INTERNAL_API_TOKEN` | optional | **required** (signs internal RPC) |

```bash
# Monolith
JWT_SECRET=$(openssl rand -hex 32) TWOFA_ENCRYPTION_KEY=$(openssl rand -hex 32) \
BILLING_PROVIDER=stripe STRIPE_SECRET_KEY=sk_live_... STRIPE_WEBHOOK_SECRET=whsec_... \
  docker compose -f deploy/compose/monolith.yml up --build

# Microservices (gateway on :8080)
JWT_SECRET=$(openssl rand -hex 32) INTERNAL_API_TOKEN=$(openssl rand -hex 32) \
TWOFA_ENCRYPTION_KEY=$(openssl rand -hex 32) BILLING_PROVIDER=stripe \
STRIPE_SECRET_KEY=sk_live_... STRIPE_WEBHOOK_SECRET=whsec_... \
  docker compose -f deploy/compose/microservices.yml up --build
```

The microservices profile is generated by `sandloom add deploy`, in the framework
and in an `sandloom new` application, which ships only the monolith profile. To
split an application, see [Split an app into
services](split-into-services.md).

Every other service waits for its migrate one-shot (`sandloom migrate upgrade-all
--apply`, `depends_on: service_completed_successfully`). In the microservices
profile each `migrate-<service>` applies the core chain + only that service's
module chain to that service's database.

## How the split works

1. **Module loading.** The plugin loader (`sandloom.core.loader.plugin_loader`)
   reads `SANDLOOM_MODULES` (JSON list) and calls each module's `register(core)`.
   Only the listed modules' routes, event schemas, and services exist in that
   process. `MODULE_WHITELIST` / `MODULE_BLACKLIST` further filter the list.
2. **Async communication** rides the durable Redis Streams bus in both profiles
   (`EVENT_BUS_BACKEND=auto` resolves to `streams` in production). Each
   service's transactional outbox lives in its own database, and its relay (one
   gunicorn worker per container) dispatches it.
3. **Sync cross-module contracts** go through the core service registry (e.g.
   billing resolves `tenancy.membership.v1`). The local provider wins when
   co-deployed; otherwise `SERVICE_BINDINGS` supplies a generated internal RPC
   proxy signed with the shared `INTERNAL_API_TOKEN`. With neither, consumers
   degrade explicitly (403/404/501) rather than failing at startup. See
   [Service RPC](service-rpc.md).
4. **Routing.** The gateway (`deploy/gateway/nginx.conf`) maps path prefixes to
   services. Adding a module = adding a `location` block.

The behaviour is pinned by `src/sandloom/core/tests/test_module_subset.py`
(any module subset boots standalone with exactly its own routes) and
`src/sandloom/core/tests/test_deploy_profiles.py` (every process environment
in both profiles validates against the production settings).

## Background work (Celery worker + beat)

Workers run the **framework** entrypoint for any application:

```bash
celery -A sandloom.core.worker worker --loglevel=INFO
celery -A sandloom.core.worker beat   --loglevel=INFO
```

`sandloom.core.worker` boots the same composition root as the API
(`SANDLOOM_COMPOSITION_ROOT`, default `sandloom.main`; a generated app uses
`<app>.asgi`) with the process's `SANDLOOM_MODULES`, resolves the Celery app through
the `taskqueue` capability (`SANDLOOM_WORKER_TASKQUEUE`, default `default`), and
imports `<module>.tasks` for every **loaded** module. A module declares tasks
with Celery's app-agnostic `@shared_task` (it never builds or imports a Celery
app) and may expose `setup_periodic_tasks(sender, **kwargs)` to schedule beat
entries. Run **exactly one beat** per broker.

## Extracting a module into its own service

1. Give the new service its own `SANDLOOM_MODULES: '["sandloom.<module>"]'`,
   `DATABASE_URL` and `BROKER_URL`.
2. Add a `migrate-<module>` one-shot with the same environment and make the
   service depend on it (`service_completed_successfully`).
3. Bind the contracts it consumes synchronously in `SERVICE_BINDINGS` (and bind
   its own contracts in the services that consume them). If it contributes
   token claims, bind its `<module>.claims.v1` from the token issuer
   (identity), with `"critical": false` iff its contributor is non-critical —
   the shipped profile binds `tenancy.claims.v1` (critical) and
   `billing.claims.v1` (non-critical) this way.
4. Add the module's path prefixes to the gateway.
5. If the module ships `tasks.py`, add a worker/beat pair with the same
   environment.

!!! warning "Steps 1–5 move code and topology, not data"
    When the module already holds data in the monolith's database, move it
    with `sandloom migrate extract-module <module> --from default --to <url>`
    (offline, in a maintenance window: it copies the module's tables, its
    `alembic_version_<module>` row and its pending outbox events, verifies
    them, and fences the source). The full procedure is the runbook in
    `deploy/README.md` → *Runbook: moving a module's data out of the monolith
    database*. Online (zero-downtime) extraction is not covered yet.

## Rolling upgrades: contract compatibility

Every module commits `contracts.snapshot.json` (the describe documents of the
contracts it provides; `sandloom contracts snapshot --write|--check`).
`sandloom contracts check --against <released snapshot>` fails CI on a breaking
contract change (removed method / parameter, newly required parameter,
incompatible type, changed kind or idempotency key); additive changes pass.
At runtime each caller compares every bound provider's live describe document
with the snapshot shipped in its own image: an incompatible provider fails
`/ready` with a `contract_incompatible` diagnostic (`CONTRACT_COMPAT_CHECK=ready`,
default; `strict` also aborts startup; `off` disables). Ship additive changes
provider-first; a breaking change is a new contract version (`.v2`).

## The image

`deploy/docker/Dockerfile` builds from the locked `uv.lock` (reproducible), runs as a
non-root user, and serves via gunicorn + uvicorn workers configured by
`sandloom.core.cli.gunicorn_conf`: the worker count honours the container CPU quota
(a non-empty `WEB_CONCURRENCY` overrides it), and the master elects exactly one
worker per container to run the outbox relay. CI
additionally builds the production image and runs a dependency vulnerability
audit (`pip-audit`, blocking CI gate).

## Production hardening

- Generate strong secrets (`openssl rand -hex 32`): production rejects short or
  placeholder values for `JWT_SECRET`, `TWOFA_ENCRYPTION_KEY`,
  `INTERNAL_API_TOKEN` and `METRICS_TOKEN`. All services share `JWT_SECRET` and
  `INTERNAL_API_TOKEN`.
- Behind a proxy, set `TRUST_PROXY_HEADERS=true` **and** `TRUSTED_PROXY_IPS`
  (CIDRs of the proxies) — see [Security Model](../reference/security-model.md#transport-request-hardening).
- Terminate TLS at the gateway or an upstream load balancer.
- Use `/health/simple` for process liveness (including Kubernetes liveness probes)
  and `/ready` for readiness. `/health` includes dependency health and may return
  `503` during a database outage; using it as liveness can cause restart loops.
- `/metrics` (Prometheus; `METRICS_TOKEN` or `INTERNAL_API_TOKEN`), `/health`,
  and `/ready` are exposed by every service. `/health` and `/ready` return `503`
  when degraded — that is the k8s probe contract. Public callers see check
  statuses only; details require `X-Internal-Token`.
- A shared multi-tenant SaaS should run with
  `PRODUCTION_PROFILE=multi_tenant_strict` (RLS on every database and tenant
  table, fail-closed revocation, a separate non-evicting security Redis, the
  contract check when split) — see
  [Production profile](../reference/security-model.md#production-profile-the-multi-tenant-trust-model-as-a-contract).
- See [Operations](../operations/runbook.md) for secrets, backups, retention, and
  observability.
